3.3

Need for source code control

Source code control maintains the revision history of the code a team works on. In DevOps, the repository also gives teams a shared place to trace the materials they use to build, operate, test and document a system. The slides’ “everything is code” principle applies to applications, infrastructure, documentation and even aspects of hardware that can be described in code.

Role What belongs in source control
Development Application source code and its revisions.
Operations Infrastructure expressed as code, such as network topology and expected package versions per server.
Quality assurance Automated tests written with tools such as Selenium and JUnit.
Documentation Product documentation and runbooks. Keeping wiki content with the service gives different roles a consistent place to find it.

A repository makes earlier versions traceable and gives teams a common reference for parallel changes. For example, the slides describe keeping a server’s expected package versions alongside the application, and keeping a service’s runbook with the service it describes.

For 5 marks. Define source code control, explain why the repository is central, then give examples from multiple roles. Close with the revision history or synchronization benefit.

3.3

Source code management tools

SCM family How history is stored Examples from the slides
SCM familyCentralized How history is storedA central server holds the full history. Examples from the slidesCVS, Subversion, Visual SourceSafe and ClearCase.
SCM familyDistributed (DVCS) How history is storedEach full clone carries the project’s history. Examples from the slidesGit, Mercurial and Bazaar.

The teacher’s slides present Git as the widely adopted DVCS with broad tooling support. Mercurial is an alternative valued for a simpler command model. Bazaar is a less common distributed alternative.

Four benefits of distributed version control

  1. Offline work. Developers can commit locally and push later when reconnected.
  2. Speed. Local operations can avoid a round trip to a server.
  3. Privacy. Developers can work locally until they’re ready to share changes.
  4. Resilience. Full clones and multiple remotes keep the history from depending on one server.

CVS is the centralized example in Unit 3.4. It uses a single repository, stores differences between versions and gives developers separate working directories so their changes can be merged. Build automation and change-request tracking are separate concerns.

3.3

Branching strategies and GitFlow

A branching strategy is the team’s agreed pattern for how work moves through branches. It determines where changes are made, how they are reviewed and merged, and how the team gets release-ready code. Choose a pattern that fits the team’s pace and pull-request workflow.

Approach in the slides How the team uses it
Trunk-based or lightweight approach Centre work on one main branch and use short-lived feature branches when needed. The slides give a fast-moving application as the example.
GitFlow Keep release-ready code on main. Use develop to integrate ongoing work. Create feature branches from develop and merge them back when complete. Use a hotfix branch for an urgent production patch so it can reach main without waiting for the next release cycle.

Two benefits to explain in an exam are a clear review and merge path for ongoing work and a predictable release path, including an urgent route for production fixes in GitFlow. The slides recommend starting with a simple model and adding branch complexity when the team needs it.

3.3

Configuration items, baselines and change control

Term Meaning and example
Basic object A single unit such as a source file, test suite or part of a specification.
Aggregate object A named collection of basic or other aggregate objects. A design specification can reference a data model and class diagrams.
Baseline A reviewed and approved version that serves as the reference point for the next change.
Version control The tools and procedures that manage revision history. Git records each revision.
Change control The process of requesting, reviewing, deciding on and applying a controlled update. A pull-request review determines whether a change can merge.

Access control determines who may change an item. Synchronization control helps prevent parallel edits from overwriting each other. For example, when two engineers edit the same configuration, a merge conflict makes the collision visible so they can resolve it before merging.

3.4

SCM system migrations

A team may migrate after a centralized tool loses support, to gain DVCS benefits, to shorten onboarding, or to fit an ecosystem that expects Git. The main decision is how much history to move. Keeping the entire history takes effort and is most valuable when old decisions or contributor attribution still matter.

Situation Decision and justification
Long-running open-source project Preserve the full history to retain attribution and trace design decisions.
Visual SourceSafe or ClearCase to Git The history models map poorly to Git. Where the cost outweighs the value, import the current codebase and keep the old system online read-only for lookups.
Subversion to Git Its history model maps more readily to Git. Mature tooling makes it practical to retain commits, authors and messages.

Migration checklist

  1. Decide on full history, partial history or a fresh start.
  2. Choose the cutover window and briefly freeze changes in the old system.
  3. Migrate and verify a sample of known commits in the new system.
  4. Retrain the team on the new tool’s workflow and branching strategy.

For a migration scenario. State the old and new systems, explain the reason to migrate, weigh the history against migration effort, then justify the decision and give the cutover steps.

Past-paper practice

2024 Q1(iv) · 5 marks · Explain the need for source code control.

Source code control records revisions of the material an organization depends on. A repository is a shared reference for application code, infrastructure configuration, automated tests and documentation. Developers work on code, Operations can keep expected server package versions as code, QA can version tests and documentation teams can keep runbooks with their services. Revision history makes changes traceable. Access and synchronization controls protect shared work by governing who can edit it and surfacing conflicts between parallel edits.

November 2024 paper · Q1(iv)

2025 Q3(iii) · 10 marks · Explain GitHub branching strategies and write any two benefits.

A branching strategy defines how changes are developed, reviewed, merged and released. Explain the two approaches in the slides.

  1. Trunk-based or lightweight approach. Use one main branch and short-lived feature branches where needed. The teacher uses a fast-moving application to illustrate a lightweight workflow.
  2. GitFlow. Keep release-ready code on main and integrate ongoing work on develop. Start each feature from develop and merge it back there when ready. Use a hotfix for an urgent production issue and bring the fix to main without waiting for the next release.

Two benefits. A known branch path makes reviews and merges easier to organize. A distinct release path keeps release-ready code identifiable and lets urgent fixes ship independently of the normal release cycle. Finish by explaining that teams should start with a simple model and add complexity only as needed.

Syllabus practice · Distinguish version control from change control.

Version control records and retrieves revisions of an object. Change control governs whether and how an update is made through request, review, decision and application. Git’s revision history illustrates version control. Pull-request review illustrates change control. A reviewed and approved baseline is the reference point for the next change.

Syllabus practice · When would you preserve full history in an SCM migration?

Preserve history when contributor credit or old design decisions matter. Give the open-source example, contrast the effort of a Visual SourceSafe or ClearCase migration with the more compatible Subversion-to-Git case, then specify what to verify at cutover.
