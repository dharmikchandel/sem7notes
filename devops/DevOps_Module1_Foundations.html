DevOps, the Dev and Ops divide, and the role of the operation team

CriticalAsked: Oct 2025, Sep 2024, Oct 2022About 25 minSyllabus 1.1

This is the most repeated question in the module. Learn what DevOps is, why it appeared, and what each side does. Then the role of the operation team is easy to write.

What DevOps is

From the slides: DevOps is a cultural movement that changes how individuals think about their work. It values the diversity of work done and speeds up how a business realises value. It breaks the wall between development, operations, quality assurance and security.

  • Gene Kim: a collaborative working relationship between Development and IT Operations, giving fast flow of planned work while increasing reliability, stability and security.
  • John Willis: a set of practices and patterns that turn human capital into high-performance organizational capital.

Why it appeared: four problems

  1. Siloed teams. Dev and Ops worked apart and released code slowly.
  2. Slow, risky releases. Big, rare releases mean bigger changesets and more risk.
  3. Manual, inconsistent operations. Hand-configured servers drift apart (environment drift).
  4. Rising expectations. Businesses wanted to ship value faster and learn from feedback.

The traditional divide

Development teamOperation team
DoesPlanning, development, testing, quality assuranceInfrastructure management, security and compliance, database administration, network
WantsFast, frequent changeStability above all
ConflictDev is rewarded for change and Ops is rewarded for stability, so each side sees the other as the obstacle. DevOps replaces this with one shared goal.

Role of the operation team

The slides show Ops handling infrastructure, security, databases and network, and the whole Ops half of the loop (release, deploy, operate, monitor). In DevOps the team stops being a gatekeeper and becomes an enabler who works with Dev from the start.

  1. Provision and manage infrastructure: servers, networks, cloud. In DevOps this is automated through scripts and infrastructure as code, not hand-set.
  2. Release and deploy: get tested software into production reliably, together with Dev, through the pipeline.
  3. Operate: keep the live service available, scaled, patched, backed up.
  4. Monitor and respond: collect metrics and logs, raise alerts, handle incidents, restore service quickly.
  5. Security, compliance and database administration: protect data and meet regulations.
  6. Feed back to Dev: pass production insight into planning so the next release is better.
  7. Collaborate: shared goals, shared on-call, blameless postmortems.

Role of the operation team

The operation (Ops) team keeps software running reliably in production. It wants stability. In DevOps it works with development as one team.

  • Infrastructure: provisions and manages servers, network and cloud, using automation and infrastructure as code.
  • Release and deploy: moves tested builds to production safely, with Dev, through the pipeline.
  • Operate and monitor: keeps the service available and scaled; watches metrics, logs and alerts; handles incidents.
  • Security and database: compliance, access control, database administration, backups.
  • Feedback: returns production data and incident lessons to the Plan phase.

Change from the old model: from gatekeeper who blocks change to enabler who shares ownership of it.

Release and deploy as phases of DevOps

  • Release phase: the build that passed testing is versioned, approved and made available. Continuous Delivery means every change is always releasable, and a human decides when.
  • Deploy phase: the release is installed in staging and then production, automatically through the pipeline. Continuous Deployment removes the manual approval step.
  • Safe deployment styles from Module 2: blue-green (two environments, switch traffic, instant rollback) and canary (5% of users first, then expand).

Differences

CI, Continuous Delivery, Continuous Deployment and the developer concepts

MajorNot asked on its own yetAbout 20 minSyllabus 1.1, 1.4

These three terms are confused all the time, and the difference between the last two is a likely short question. The same ideas also support the release and deploy answer in Lesson 3.

TermMeaning
Continuous Integration (CI)Developers merge into a shared mainline often. Every merge triggers automated tests, so problems are caught early. "Green" means the build is clean; "red" means it is broken.
Continuous DeliveryCI plus automated proof that every change is always deployable. A human decides when to release.
Continuous DeploymentEvery change that passes the tests goes to production automatically. No manual gate.

Jez Humble's point: Continuous Delivery is general and fits even embedded and IoT software. Continuous Deployment is specific to web software, because you cannot auto-deploy to a physical device the same way.

Development, release and deployment concepts (unit 1.4)

Version control
Records changes as commits with who and when. You can compare, merge and restore, so production can be reverted to a previous version. Example: Git.
TDD
Write a failing test first, write the code, then make the test pass. Shorter feedback loops, and developers own quality.
Application deployment
Planning and executing delivery of a release. The approach should match the app: a database update needs strict consistency, a static page does not.
MVP
The prototype with the minimum effort needed to test whether an idea is good. Less is wasted if big changes are needed.

Beyond DevOps and examples

  • NoOps: Dev and Ops never interact directly, often through serverless. MLOps: managing the machine learning lifecycle in production. DevSecOps: security built into every stage.
  • Users of DevOps in industry: AWS, Netflix, Walmart, Target, Hertz, Fidelity. It is not tied to one domain.
Answer sheet: CI vs Continuous Delivery vs Continuous Deployment 5 marks

CI, Continuous Delivery and Continuous Deployment

  • CI: frequent merges to a shared mainline, each triggering automated build and tests.
  • Continuous Delivery: every change is proven deployable by automated tests; a human decides when to release.
  • Continuous Deployment: every change that passes goes to production automatically.

Draw the pipeline: commit, CI, artifact repository, staging, manual approval, production.

Benefit: small, frequent, tested changes catch regressions early and reduce risk.

The 2023 question asked for a DevOps success story of any one organization under four headings: profile, one major issue, actions taken, benefits. Check this against your slides

If your professor showed different numbers, write those. Etsy alone is enough for "any one organization".

The four headings

1. Profile
Etsy is an online marketplace for handmade and vintage goods, based in Brooklyn. Your Module 2 slides put it at about 800 staff. In 2014 it reported about 150 engineers, around 60 million visits and 1.5 billion page views per month.
2. Major issue
Releases were large, rare and risky. A typical website released about every two weeks, and pushing code needed many people on standby. Development and operations were separate teams with different goals, which slowed delivery and made each deploy stressful.
3. Actions
  • Continuous Integration: a full test suite runs before every deploy (over 14,000 test runs a day).
  • "Princess" staging environment: a production-like copy for employees, so code is checked before it is live.
  • Deployinator: a one-button deploy tool, so one person pushes a change in about two minutes. Etsy open-sourced it in 2015.
  • Config flags (feature flags): new code ships switched off, then is turned on gradually.
  • Monitoring for everyone: dashboards and graphs open to all; developers watch their own features.
  • Culture: everyone deploys, even on their first day; postmortems are open to the whole company; a dedicated channel for outage coordination; sharing through blog posts and open-source tools.
4. Benefits
From roughly one release every two weeks to about 50 deploys a day. Small changes meant lower risk and quick rollback, faster experiments and learning, a stronger collaborative culture, and a reputation that attracts engineers.
Say it in one line

Etsy turned painful fortnightly releases into around 50 safe deploys a day by combining CI, a one-button deploy tool, feature flags, open monitoring and a blameless, shared-ownership culture.

DevOps as a folk model, outputs vs outcomes, and the metrics

CriticalAsked: Sep 2025 (folk model), Sep 2024 (metrics), Oct 2022 (output vs outcome)About 25 minSyllabus 1.2

Three separate questions live in this lesson. The folk model is the hardest to explain well, so it comes first and is built from a plain idea: a shared shorthand that people use without checking that they all mean the same thing.

What a folk model is

From the slides: a folk model is a mental model that is not necessarily accurate in the real world, so it can lead to wrong decisions, but it is shared among members of a culture.

  • Cultural model: a small set of concepts and the relations between them, shared by a social group (a cognitive schema).
  • Intersubjective sharing: everybody in the group knows the schema, and everybody knows that everyone knows it.
  • Instantiation: fitting real people and events into the roles of the schema. The "buying" schema has purchaser, seller, merchandise, price. "John bought a hat at the bookstore" fills those roles.

In cognitive science, a folk model is a simplified stand-in for a more complex idea. "The cloud" is the example: people say "the internet", "Google Drive" or "a data centre". All are useful and none is precise.

Why DevOps is a folk model

  • People use "DevOps" for CI/CD, automation or testing, so it became a buzzword. To one person it is a job title, to another Docker, to another a culture. The real thing behind the buzzword is culture.
  • The model of DevOps is rarely taught. It is learned from observations, with the gaps filled by common sense.
  • Useful: a quick shared shorthand. Problematic: groups use the same word with different intent and argue about definitions instead of ideas. Example: one teammate says "make it modular" meaning separate files, another builds microservices.

Getting past the definition trap: do not argue what DevOps means. Describe an exaggerated bad behaviour, such as a "DevOps team" that only passes messages between Dev and Ops. The good behaviour then becomes obvious.

Significance

  1. It shows DevOps is about culture and shared understanding, not a tool or a job title.
  2. It explains why teams miscommunicate and argue over definitions.
  3. It tells us how to spread DevOps: with stories and examples, including exaggerated bad ones.
  4. It leads to changing what we measure: outcomes, not only outputs.

Outputs vs outcomes

Outputs

  • What the organization actually delivered.
  • Example: a new key feature shipped in a release.

Outcomes

  • What the organization gains from those outputs.
  • Example: more revenue, better customer retention, lower operating cost.

The four metrics

Remember

Two measure speed (lead time, deployment frequency). Two measure stability (change failure rate, time to restore). The 2024 paper has "change failure rate, lead time" pencilled beside the question.

The old view and the new view of human error

CriticalAsked: Sep 2025, Sep 2024About 20 minSyllabus 1.2

The 2024 paper asked for "the mindset that sees human errors as structural rather than personal". That is the new view, so one lesson covers both questions.

Old view: "bad apples"

  • "Human error is the cause of trouble."
  • Goal is to eliminate human error.
  • Blame the "bad apples" and remove them.
  • Assumes malice or incompetence.
  • Individuals are blamed, shamed or fired.
  • A culture of fear that blocks communication and transparency.

New view: "a symptom of deeper trouble"

  • "Human error is a symptom of trouble deeper in the system."
  • Errors are structural, not personal.
  • People act on the context they are in, not out of malice.
  • Examine the system as a whole, not individuals in isolation.
  • Every error is a shared learning opportunity.
  • A blameless environment, handled cooperatively.

Examples to write

  • 2 AM crash. Old view asks "Who pushed that code?" New view asks "What in our process let a broken script reach production unchecked?"
  • Airline. Firing the pilot after a crash, without asking why the warning system failed, lets the next pilot make the same mistake.
  • DROP TABLE. A junior developer drops a production table. New view: why was an unreviewed command allowed to run in production?

Why the new view wins

  1. Builds trust: more transparency within a team.
  2. Prevents repeats: colleagues learn without repeating costly mistakes. GitLab and Cloudflare publish public postmortems for this reason.
  3. Fuels innovation: more time solving new problems instead of old ones.

With the new view, issues become repairs, not blame: repair misunderstandings about who works on what, repair bugs that expose gaps in expected behaviour, and repair process and documentation when production does not match expectations.

Answer sheet: old view vs new view of DevOps 5 marks

Old view vs new view

They are two mindsets toward human error. The mindset you choose decides whether the culture is one of fear or of learning.

  • New view: human error is a symptom of deeper system trouble; errors are structural; people act on their context; examine the whole system; blameless learning.

Example: a 2 AM crash. Old: "who pushed it?" New: "why did the process let it through?" Result: trust, no repeats, innovation.

The 2022 option asked: "Which methodology focuses on both software development and IT operations? Explain its principles to achieve the goal." The answer to the first sentence is DevOps. For the principles, your slides give the DevOps Compact and the key takeaways, so use those.

The Compact: three principles

The heart of DevOps starts with people working as teams with a shared desire for mutual understanding.

1. Shared, clearly defined goals2. Ongoing communication3. Dynamic repair of understanding
  • Shared goals: a backend and frontend team agree the API contract up front.
  • Communication: they message each other when blocked.
  • Repair: they adjust the plan when something breaks.

The climber and belayer

Rock climbing depends on communication, clarification and mutual trust, just like the compact.

Trust but verify: before the climb, each person checks their own equipment and then each other's. In a workplace, trust your partner's competence and still check the work before it moves on.

DevOps and its principles

The methodology that unites software development and IT operations is DevOps. It is a cultural movement that breaks the wall between Dev, Ops, QA and security, and joins plan, code, build, test, release, deploy, operate and monitor in one loop.

Principles (the DevOps Compact):

  • Shared, clearly defined goals between Dev and Ops.
  • Ongoing communication and mutual understanding.
  • Dynamic repair of understanding: problems lead to repairs, not blame.
  • Trust but verify: trust competence, check the work (the climber and belayer).

Supporting principles:

  • Culture over tools.
  • Small, frequent, automated change (CI/CD).
  • Visibility through dashboards and metrics.
  • Blameless learning from failures.

Outcome: faster delivery with more reliability and stability.

Methodologies behind DevOps: development, operations, systems

MajorNot asked yet (syllabus 1.3)About 25 minSyllabus 1.3

A methodology splits work into phases. Many treat development and operations as separate, which creates conflicting goals. DevOps does not prescribe one: it asks you to assess which fits your environment. A 5-person startup might use Agile loosely; a bank might combine Agile and ITIL.

Three lenses

Software development

  • How to structure and pace writing code
  • Waterfall, Agile, Scrum

Operations

  • How to structure and govern running IT services
  • ITIL, COBIT

Systems

  • How to think about the whole system, maximising value and minimising waste
  • Systems thinking, Lean

Software development methodologies

Waterfall
Sequential: requirements, design, implementation, integration, testing, installation, maintenance. You cannot start the next stage before the last. Adapted to software in the early 1980s.
Agile
A group of lighter, more flexible methods. The 2001 manifesto values: individuals and interactions over processes and tools; working software over comprehensive documentation; customer collaboration over contract negotiation; responding to change over following a plan.
Scrum
By Ken Schwaber and Jeff Sutherland. Work in sprints of one week to one month. The Daily Scrum asks: what did I do yesterday, what will I do today, what is blocking me? The Scrum Master facilitates and removes blockers.
Is DevOps just Agile?

No. DevOps grew around Agile but extends it to the whole organization. Agile organises developers' sprints. DevOps also asks how the same team handles deployment, monitoring and incidents.

Operations methodologies

ITIL
A set of best practices for IT services; first published in 1989 by the British CCTA. Five core sections: Service Strategy (align business goals and customer needs), Service Design (the four Ps: People, Processes, Products, Partners), Service Transition (build, test and deploy changes in a coordinated way), Service Operation (daily running; fulfil requests, fix failures), Continual Service Improvement (learn from past successes and failures).
COBIT
An ISACA framework for governance and management of IT, first released in 1996. Core idea: align business goals with IT goals. Five principles: meet stakeholder needs; cover the enterprise end to end; apply one integrated framework; enable a holistic approach; separate governance from management.

Systems methodologies

Systems thinking
Think about the whole system, not just development or operations. Ask "what else does this touch?" before changing a part.
Lean
From Toyota's production system (Womack, Jones and Roos). Five principles: define value, map the value stream, create flow, establish pull, pursue perfection. Goal: maximise customer value and minimise waste.
Waste in software (Poppendieck)
Partially done work, extra features, relearning, unnecessary handoffs, task switching, delays, defects.
One incident, three lenses

A fest app crashes in production. Agile and Scrum shaped how it was built. ITIL and COBIT shape how the incident is handled. Lean asks whether the whole process wasted anyone's time.

ConceptWhat it isExample

Extra terms from unit 2.3 (infrastructure automation)

Infrastructure as code (IaC)
Provision infrastructure through code, not manual clicks. Version it, test it and review it. Tools: Terraform (cloud), Ansible (configuration), Helm (Kubernetes).
Configuration drift
Servers slowly change away from their desired state through manual patches and one-off fixes, until no two are alike.
Snowflake server
A server so uniquely hand-configured that nobody can rebuild it. Fragile and irreplaceable.
MTBF, MTTR, availability
Mean time between failures; mean time to repair. Availability = MTBF ÷ (MTBF + MTTR). "Four nines" (99.99%) means under an hour of downtime a year. IaC lowers MTTR because re-running the script rebuilds the server.

Cultural concepts and the generative culture

CriticalAsked: Sep 2023 (generative culture)About 20 minSyllabus 1.4

These are the concepts about how organizations deal with and learn from incidents and failures. The generative culture is the one that has been asked. The others are short and support it.

ConceptWhat it is
RetrospectiveA discussion after a project is finished, usually regular (every quarter) or at project end. Three topics: what happened, what went well, what went poorly.
PostmortemHappens after an unplanned incident or outage. A systemic postmortem has a timeline from logs, a debrief where everyone shares their view, and remediation items to prevent a repeat.
BlamelessnessFrom John Allspaw's blameless postmortems. It is not about letting people off the hook. It lets people come forward with full details, even if their own actions contributed, so real learning can begin.
Organizational learningCollecting, growing and sharing an organization's knowledge through deliberate steps. After an outage, fix the bug and update onboarding documents so every new hire learns it.

The Westrum model of organizational culture

Sociologist Ron Westrum found that how information flows through an organization predicts its culture and performance. There are three types.

PathologicalBureaucraticGenerative
OrientationPowerRulesPerformance
InformationHoarded or distorted for political gainStays inside departmentsFlows freely
CooperationFear and threat are commonModest; teams protect their own turfHigh cooperation and trust
Failure leads toScapegoatingLittle concern for the overall missionInquiry, not blame

Why DevOps aims for a generative culture

  • DevOps is fundamentally about culture. If the culture is not supportive, an organization will not become high-performing, however good its tools are.
  • Trust and cooperation across the whole organization, not just within teams.
  • Better decisions because better information reaches the decision-makers.
  • Open, transparent teams where hierarchy matters less than the mission.
The pilot example

A pilot reports a near miss. A pathological culture silences the pilot to avoid bad publicity. A bureaucratic one files the report and ignores it. A generative one investigates, so a near miss does not become an accident.

Last-hour sheet

Read this just before the exam

DevOps
A cultural movement. Breaks the wall between Dev, Ops, QA, security. Born from siloed teams, slow risky releases, manual ops, rising expectations.
Dev vs Ops
Dev: plan, code, test, QA; wants change. Ops: infrastructure, security, database, network; wants stability. Role of Ops in DevOps: infrastructure, release and deploy, operate, monitor, security, feedback; gatekeeper becomes enabler.
Loop
Plan, Code, Build, Test | Release, Deploy, Operate, Monitor, back to Plan.
Pairs
Compile = source to object code; Build = compile + test + package. Release = approve and version; Deploy = install. Operate = run; Monitor = observe. Output = shipped; Outcome = gained.
CI / CD
CI = merge often, test every merge. Delivery = always deployable, human releases. Deployment = automatic to production.
Etsy
Fortnightly risky releases to about 50 deploys a day: CI, Princess staging, Deployinator, config flags, open monitoring, blameless culture.
Folk model
Shared mental model that may be inaccurate. "DevOps" is one. Escape the definition trap with exaggerated bad behaviour.
Metrics
Lead time, deployment frequency, change failure rate (0 to 15%), mean time to restore.
Old vs New view
Old: human error is the cause; blame bad apples. New: human error is a symptom of deeper system trouble; blameless; shared learning.
Compact
Shared goals, ongoing communication, dynamic repair of understanding. Trust but verify.
Methodologies
Waterfall, Agile, Scrum (dev); ITIL, COBIT (ops); Lean: value, value stream, flow, pull, perfection (systems).
Infrastructure
Configuration management, cloud, infrastructure automation, artifact management, containers. Plus IaC, configuration drift, snowflake server, MTBF, MTTR.
Culture
Retrospective (planned), postmortem (after an incident), blamelessness, organizational learning. Westrum: pathological (power), bureaucratic (rules), generative (performance, trust, inquiry not blame).
