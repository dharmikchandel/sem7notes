5.1

Why deployment systems are needed

A deployment system automates the journey from code to a running application. An automated pipeline repeats the same steps, records what happened and reduces reliance on one person following a manual checklist.

NeedSpeed What it achievesShorter release cycles and smaller, more frequent changes Teacher’s exampleAmazon’s frequent deployments in the slide’s historical example
NeedConsistency What it achievesSame artifact across environments Teacher’s exampleBuild one container image and use it on test servers and production
NeedSafety What it achievesEarly failure detection and quick rollback Teacher’s exampleKnight Capital’s manual rollout missed a server running old code. The slide uses it to show the cost of a missed step.
NeedScale What it achievesRepeatable releases across many servers and services Teacher’s exampleOne pipeline template can serve login, cart and payment services that release independently
Challenge Example and response from the slides
Environment drift Staging may run Java 17 while production runs Java 11. Define infrastructure as code and ship the same container.
Risky releases or downtime A bad checkout release during a sale can affect every user. Use a canary or keep a blue-green rollback path.
Database changes A renamed column can break the old version still running. Add the new field, migrate the data, then remove the old field in safe steps.
Secrets and security A committed API key can leak quickly. Store secrets in a vault and scan commits.
Resource sizing CPU requests that are too large waste capacity. A limit that is too low causes throttling. Set requests and limits from usage.
Skills and culture Train the team and share responsibility for releases.

5.1

A/B, canary and blue-green

Strategy Goal Traffic and release decision Recovery
StrategyA/B testing GoalMeasure which feature or design performs better Traffic and release decisionRoute user groups to control and variant concurrently. Compare conversions, click-through or engagement and assess statistical significance. RecoveryDisable the variant if needed.
StrategyCanary testing GoalValidate a risky release on a small population Traffic and release decisionGive the new version a small traffic share. Check errors, latency and CPU, then increase traffic in steps while service objectives hold. RecoveryHalt promotion and revert on threshold breach.
StrategyBlue-green GoalSwitch between two production-equivalent environments Traffic and release decisionBlue serves users while Green is tested. Route production traffic to Green after validation. RecoverySwitch back to warm Blue. Parallel environments cost more to run.

A/B testing

Bucket users by ID, cookie or segment and send each group to a version through a router or feature flag. A 50/50 split is one option. In the teacher’s Netflix thumbnail example, the custom artwork variant has a higher click-through rate than the generic screenshot. The experiment uses viewer behaviour to select a winner.

Canary

The slide’s rollout diagram uses 1% → 10% → 50% → 100% as an example. At each step compare metrics with the baseline or SLO. The Google/Kubernetes example in the deck uses one canary pod and illustrative rollback thresholds of error rate over 0.1% or P99 latency over 200 ms.

Blue-green

Provision Green with the new version, run smoke tests and health checks, then switch traffic. Hold Blue ready to serve if Green fails. In the slide’s e-commerce example a load balancer shifts traffic to Green and Blue remains warm for rollback.

Apply the strategies in Kubernetes

  • A/B: a router or service mesh directs a user segment or header to a version. The deck names Istio and Flagger.
  • Canary: use weighted steps and Prometheus checks to promote or roll back with Argo Rollouts or Flagger.
  • Blue-green: keep two Deployments and switch the Service selector from Blue to Green.

For a compare-and-choose answer. Identify the primary goal first. Use A/B to compare outcomes, canary to limit exposure and validate health, and blue-green for a fast environment switch with a warm fallback.

5.1

Monitoring, alerts and dashboards

Monitoring continuously observes a system so a team can detect problems early, recover faster, protect response times and uptime, and right-size resource use. The slide example compares discovering checkout errors from morning complaints with an alert at 02:01 and rollback by 02:20.

Golden signal What it measures Example
Golden signalLatency What it measuresTime taken to serve requests ExampleP99 response time
Golden signalTraffic What it measuresDemand on the system ExampleRequests per second
Golden signalErrors What it measuresFailed work ExampleShare of requests returning 5xx
Golden signalSaturation What it measuresHow close resources are to capacity ExampleCPU or memory pressure

Metrics are numeric time series such as CPU use. Logs record events such as a database timeout. Traces follow a request across services. A metric can show a symptom, while logs and traces help locate its cause.

Real-time alerts

Make the alert actionable, link it to user impact and assign an owner and severity. Match the channel to urgency. A site outage can page the on-call engineer, disk usage at 80% can send a team message and a finished deployment can add a dashboard note. Group related alerts and tune thresholds so repeated low-value alerts do not hide a real incident. The slide example alerts on an error rate above 1% for five minutes.

Dashboards

A dashboard groups signals for its audience. Business users need uptime, orders and incidents. Engineers need latency, errors and deployment context. Operations needs capacity and node health. Use a small set of panels, show trends, label status and link alerts or runbooks. Instrument services to reduce blind spots, sample data when volume is high, and set retention limits.

5.2

Docker and the container workflow

Docker packages an application and its dependencies so the same image can run on a developer laptop, a test server and production. The dependency mismatch illustrated in class is a Python application that needs 3.11 on a server with 3.8. Containers share the host kernel and start quickly. VMs run a guest OS and provide stronger isolation.

FROM python:3.11-slim
COPY . /app
RUN pip install -r /app/req.txt
CMD ["python", "/app/main.py"]

The slide’s FROM selects the base image. COPY adds the application files. RUN installs dependencies during build. CMD specifies the startup command. A registry makes a tagged version available for deployment.

For 5 marks on the need for Docker. Start with an environment mismatch, draw Dockerfile → image → container, and explain consistency, portability, fast startup and resource efficiency.

5.2

Kubernetes architecture and orchestration

Kubernetes automates deployment, scaling and management across a cluster. The control plane responds to changes in desired state and decides where to run workloads. Worker nodes run the application pods.

Part What to label in the diagram
API server Entry point for cluster operations and deployment requests.
etcd State store for cluster data.
Scheduler Chooses a node for each unscheduled pod.
Controller manager Runs controllers that reconcile actual state with desired state.
Kubelet Node agent that acts on pod specifications and starts containers through the runtime.
Container runtime Pulls container images and launches containers.
Pod Smallest deployable unit that wraps one or more containers.

A Deployment maintains the desired replicas and handles updates. A Service gives the pods a stable address and balances traffic. In the deck’s example, a three-replica Deployment runs behind one Service.

Orchestration adds self-healing, scaling, service discovery, load balancing and rolling updates. The sale-day example scales from 3 to 30 pods and back to 3. A resource request informs scheduling. A limit caps use. CPU above the limit is throttled, and a container exceeding its memory limit can be killed.

5.2

CI/CD pipeline with GitHub Actions

CI integrates small changes frequently and builds and tests them automatically. Continuous delivery keeps passing changes ready for a production release, with approval where required. Continuous deployment automatically releases passing changes.

Term Meaning
Workflow YAML automation file under .github/workflows/.
Event Trigger named under on, such as push, pull_request, schedule or workflow_dispatch.
Job Set of steps executed on one runner. Jobs can run in parallel unless dependencies are declared.
Step and action A step runs a shell command or calls a reusable action.
Runner Execution machine. GitHub-hosted runners give a fresh supported environment. Self-hosted runners can reach special hardware or networks and require maintenance. 
on: push
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci && npm test

This is the slide’s first workflow. GitHub starts it on a push, assigns a runner and reports the result on the commit. Add needs: test on a build job and needs: build on deployment to enforce the order. The class example restricts deployment to main.

  • Package and deploy. Log in to the registry, tag the image with the commit SHA and push it. Use cluster access to apply manifests and check rollout status with kubectl rollout status.
  • Secrets and approvals. Use repository or environment secrets and give tokens least privilege. Environments can require reviewers so staging deploys automatically and production waits.
  • Speed and reliability. Cache dependencies, test versions in parallel with a matrix, reuse actions and use path filters. Run fast checks first, pin and review actions, fix or quarantine flaky tests and cancel outdated runs.

5.2

Infrastructure as Code, Terraform and Ansible

Infrastructure as Code (IaC) represents servers, networks and storage in versioned files. It makes environments repeatable, reviewable and faster to recreate. The slides use manual edits and differing server setups to illustrate configuration drift.

Declarative code describes the desired end state, such as three servers. The tool works out the steps. Imperative code specifies steps in order. Idempotence means applying the same desired configuration again has the same result once the target state is reached.

Aspect Terraform Ansible
AspectMain role TerraformProvision infrastructure such as instances and networks AnsibleConfigure packages, files and services on hosts
AspectLanguage TerraformHCL configuration AnsibleYAML playbooks
AspectHow it tracks or reaches targets TerraformState maps configuration to real resources AnsibleAgentless in the slide example, using SSH from a control node
AspectReuse TerraformModules for reusable infrastructure AnsibleRoles for reusable tasks, shared through Galaxy
AspectReview or protection TerraformReview terraform plan, store state remotely with locking AnsibleCheck mode where supported, Vault for secrets

Terraform providers connect to platforms. A resource declares what to create. Variables parameterize settings such as instance size, outputs expose values such as server IPs and modules group reusable blocks. The state file maps configuration to infrastructure, so teams use remote state and locking to coordinate changes. Review a plan before applying and require approval for changes that could delete resources.

An inventory lists managed hosts. A playbook specifies tasks, and a module performs a unit of work, such as installing packages or managing a service. The deck’s playbook targets the web group, uses become: true and ensures nginx is installed with apt and state: present.

For the 200-server drift scenario. Explain the risk of inconsistent manual edits. Keep the desired package and service configuration in a versioned playbook, target the servers through inventory and reapply the same configuration. Review changes and protect secrets with Vault.

5.2

AWS Lambda and Azure Functions

Serverless shifts server management and scaling to the cloud provider. The deployable unit is a function. Events such as an upload, timer or HTTP request invoke the function, which can save a result, return a response or notify another service.

Aspect AWS Lambda Azure Functions
AspectTriggers AWS LambdaAPI Gateway HTTP requests, S3 uploads, EventBridge schedules or events, SQS/SNS messages Azure FunctionsHTTP, timer, Blob Storage and queue
AspectDeploy AWS LambdaPackage code as a ZIP or container image, upload and connect an event source Azure FunctionsDevelop and test locally with Functions Core Tools, then publish a Function App
AspectIntegration AWS LambdaLambda event and context are passed into the handler. Step Functions orchestrates workflows. Azure FunctionsBindings connect functions to services with less glue code. Durable Functions supports workflows.
AspectRollout example AWS LambdaWeighted aliases for canary traffic Azure FunctionsDeployment slots and swap for blue-green

The benefits include automatic scaling, usage-based costs on relevant plans, rapid deployment and reduced infrastructure work. Good fits in class are short event-driven tasks, scheduled jobs, spiky traffic and small APIs. Long-running work, large stateful apps or consistently low latency requirements can fit poorly. A cold start is the additional latency of initializing a fresh execution environment. Small packages and provisioned concurrency in the Lambda example help reduce it.

Keep functions small and stateless, right-size memory and timeout, store secrets separately, and monitor errors and cost. In the slide pipeline, push triggers tests, packaging, deployment, then monitoring.

5.3

Prometheus, Alertmanager and Grafana

Cloud workloads change as services scale and pods restart. Monitoring must discover targets, collect time-series metrics, alert on symptoms and share dashboard views.

Prometheus pulls metrics over HTTP from endpoints such as /metrics on a schedule. Applications can expose metrics directly. Exporters expose metrics from systems that need an adapter. Node Exporter provides host CPU, memory and disk metrics, cAdvisor provides container usage, and kube-state-metrics exposes Kubernetes object state.

Metric type Meaning and example
Counter Cumulative total that rises until reset, such as total requests.
Gauge Value that can rise or fall, such as memory in use.
Histogram Observations counted in buckets, such as request-response times.
Summary Observations with quantiles computed in the instrumented application.

A job groups scrape targets. The following is the static target example from the deck. In Kubernetes, service discovery can find changing targets automatically.

scrape_configs:
  - job_name: "web"
    scrape_interval: 15s
    static_configs:
      - targets: ["web1:8080"]

PromQL and notifications

up
rate(http_requests_total[5m])
sum by (job) (rate(http_requests_total[5m]))

up shows successful scrapes. rate(...[5m]) estimates the per-second increase over five minutes. sum by (job) combines that rate by job. The deck’s alert rule checks up == 0 for two minutes to avoid reacting to short blips. Alertmanager groups, silences and routes alerts to channels such as Slack or email.

Grafana

Grafana queries sources such as Prometheus and displays their data. A data source supplies the data, a panel presents a particular view and a dashboard groups panels. Use time-series panels for trends, stats for one number, gauges against a limit and tables for details. Variables and time-range controls help focus diagnosis.

In Kubernetes the slides show a Helm chart installing Prometheus, Alertmanager and Grafana. High-cardinality labels and long retention increase storage use. Limit label values, set retention and group related alerts. Compare actual CPU with requests and actual memory with limits to right-size pods.

5.3

Centralized logs and the ELK stack

Logs spread over servers and short-lived containers are hard to search together. Centralization keeps events available after restarts and lets teams trace requests, debug faster, audit activity and apply retention. Application logs record code events, system logs record OS and service events, access logs record web requests and audit logs record who did what and when.

Component Purpose
Beats Lightweight shippers. Filebeat sends log files, Metricbeat sends system metrics and Packetbeat sends network data.
Logstash Accepts inputs, parses or enriches using filters, and forwards to outputs. A grok filter can turn a raw text line into searchable fields.
Elasticsearch Stores and searches JSON documents. An index groups documents, and shards distribute pieces of an index.
Kibana Web interface to search in Discover, build visualizations and combine panels in dashboards. KQL filters records.

The teacher’s basic Logstash configuration listens for Beats on port 5044 and sends events to Elasticsearch. A filter is optional in this example.

input {
  beats { port => 5044 }
}
output {
  elasticsearch { hosts => ["localhost:9200"] }
}

The slide’s grok example parses a GET /login access-log entry with status 500 into client IP, HTTP verb, path and response fields. In Kibana, response: 500 and request: "/login" narrows the error search to the login path.

For Kubernetes, have applications log to stdout. Nodes keep the files and Filebeat can run once per node through a DaemonSet. Use structured JSON logs and a request or trace ID, mask sensitive data before shipping, and set index retention. Filter noisy logs and use hot, warm and cold tiers when appropriate. Prometheus metrics can surface a spike and centralized logs can explain the events behind it.

5.3

Incident management and PagerDuty

An incident is an unplanned event that interrupts or degrades a service. A workflow gives the team owners, roles, actions and a record of lessons from the failure.

Step What to do
Detect Find the issue through a monitoring alert, a log spike or a support ticket.
Respond Acknowledge, assess impact, set severity, declare an incident if needed and assign roles.
Mitigate Restore service quickly by rolling back, failing over, scaling or disabling a feature.
Resolve Check that metrics are healthy, close the incident, update stakeholders and plan the permanent fix.
Learn Write a blameless postmortem with the timeline, root cause and actions with owners and dates.

The slide’s severity example pages immediately for SEV 1 (most users affected) and SEV 2 (key feature broken), responds in hours for SEV 3 and opens a ticket for SEV 4. The incident commander leads, the technical lead investigates, communications updates stakeholders and the scribe records the timeline. Measure MTTD (detect), MTTA (acknowledge), MTTR (resolve, as used in the slides) and incident count.

PagerDuty receives alerts from monitoring tools and routes them to the responsible engineer using on-call schedules. Escalation calls another engineer if the first does not respond. Notifications can use push, SMS, phone or email. The slides also cover alert management, incident tracking, automation and incident analytics.

Example from the slides. 02:00 Prometheus detects an error-rate spike. 02:01 PagerDuty pages the primary on-call engineer. 02:05 the alert is acknowledged and rollback starts. 02:20 the incident is resolved and a postmortem is scheduled.
