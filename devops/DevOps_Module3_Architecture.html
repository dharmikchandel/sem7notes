Functional and non-functional requirements

CriticalAsked: Sep 2024 (learning management system)About 20 minSyllabus 3.1

Every architecture question starts from requirements. The slides split them into two kinds. Learn the split, the pipeline example, and what DevOps demands of an architecture.

Functional requirements

  • Describe what the system must do.
  • Specific services, features and reactions.
  • Map directly to use cases.
  • Tested by checking the function runs.
  • E.g. "Send an irrigation alert via SMS."

Non-functional requirements

  • Describe how well it must behave.
  • Quality attributes: performance, security, usability limits.
  • Often apply across the whole system.
  • Often decide acceptance or rejection.
  • E.g. "Alerts delivered within 5 seconds."

Slide example: functional is "handle credit card transactions"; non-functional is "handle several per second".

The slide's DevOps example: an online shop built with a pipeline

Functional

  • Developers push source code to Git.
  • A Git push triggers the CI pipeline.
  • The pipeline compiles the application.
  • The pipeline runs automated tests.
  • A successful build creates a Docker image.
  • The image is deployed to Kubernetes.
  • Prometheus collects metrics.
  • Developers are notified when a pipeline fails.

Non-functional

  • The CI pipeline completes within 10 minutes.
  • 99.9% availability.
  • Supports 100 concurrent deployments.
  • Deployment credentials are encrypted.
  • A failed deployment is recoverable within 5 minutes.
  • Pipeline logs are retained for 30 days.

A good non-functional requirement has a number in it. Notice how each one above is measurable.

What continuous delivery demands of architecture

1. Deploy small changes often

From a developer's machine to production quickly, as the normal case.

2. High confidence in quality

Rolling back because of surprise problems should be rare.

Requirements of a learning management system (LMS)

Functional requirements describe what the system must do: the specific services and behaviours, which map to use cases and are tested by checking that the function runs.

  • A student shall register and log in.
  • A student shall enrol in a course and view or download materials.
  • A student shall submit assignments and take quizzes.
  • An instructor shall upload content, grade submissions and publish results.
  • The system shall notify users of deadlines and grades.

Non-functional requirements describe how well the system behaves: quality attributes that often apply across the whole system and decide acceptance.

  • Performance: a page loads within 2 seconds.
  • Scalability: supports 5,000 concurrent users during an exam.
  • Availability: 99.9% uptime.
  • Security: passwords and student records are encrypted; role-based access.
  • Usability: works on mobile screens.
  • DevOps-related: a failed deployment is recoverable within 5 minutes; small changes can be released often without taking the whole LMS down.

Why it matters for DevOps: continuous delivery needs small changes deployed often, with high confidence in quality. The non-functional requirements are what push the design towards modular architecture.

The monolithic scenario: one typo, one giant archive

MajorNot asked on its own yetAbout 10 minSyllabus 3.1

This is the story that motivates the whole module. A large web application has many functions, plus a static website inside it. It deploys as a single Java EE application archive. To fix one typo on the static site, you rebuild and redeploy everything. Example: correcting "Wellcome" to "Welcome" in a footer means rebuilding a business-critical system.

The "simple" fix, in four steps

  1. Branch the monolith's code to match what is running in production.
  2. Make the change on the branch: correct the spelling.
  3. Build a new artifact with the correction, and version it.
  4. Deploy the new artifact to production.

The hidden costs of "just a typo"

  • If something breaks during deployment, the whole business loses revenue.
  • Real mental energy goes into proving a trivial change is safe ("we also touched some version strings, is that safe too?").
  • Every change to a monolith needs the full manual verification chain. Example: a five-minute spelling fix triggers a two-hour regression test of an unrelated checkout flow.

What went wrong

There was no modularisation, at least from a deployment point of view. The fix belongs to a frontend web component, which could be deployed on its own life cycle, alone. A standalone frontend deployment pipeline would fix the typo in minutes, untouched by the backend.

One-line takeaway

A monolith turns even a spelling fix into a full, risky redeploy. That is the opposite of "small changes, deployed often, with confidence".

Check yourself

What was the main architectural problem in the typo story?

The static website could have deployed on its own.

Architecture rules of thumb: separation of concerns, cohesion, coupling

CriticalAsked: Sep 2025 (inventory system)About 25 minSyllabus 3.1

Three connected ideas. The key insight ties them together, and it is the line examiners want to see.

Separation of concerns

Consider different aspects of a system separately from one another. Divide the system into distinct concerns, each with one specific responsibility.

User interface displays products, accepts input
Business logic ordering, pricing, discounts
Database customers, products, orders
Security authentication and authorisation
Logging records activity and errors
Monitoring tracks health and performance

The slide's example is an online shopping application with exactly these six concerns.

Cohesion

  • The degree to which the elements of a module belong together.
  • How strongly related a module's functions really are.
  • We want it high.
  • E.g. a SpellChecker module that only checks spelling.

Coupling

  • The degree of dependency between two separate modules.
  • We want it as low as we can make it.
  • E.g. the static website module should not need to know about the payments module.
The key insight

High cohesion + low coupling = separation of concerns, automatically, and it works in reverse too. The monolith failed because it had low cohesion and high coupling: concerns were never separated.

Applying it to an inventory system

Stock UI→Stock logic add, remove, reorder→Inventory database

Separate concerns: user interface, stock logic, database, security, logging and monitoring. Keep each module cohesive (the reorder module only handles reordering) and loosely coupled (reports read stock through one interface and never touch the database tables directly).

Not in your slides: the "three principles" mapping

If the question asks for three design principles (for example "optimise for change, design for operations, automate everything repeatable"), your slides do not define them. Use this method: say what the principle means in one line, then tie it back to the slide ideas.

Optimise for change: small, independently deployable modules (low coupling). Design for operations: monitoring and logging as their own concerns, so the system can be run and observed. Automate everything repeatable: build, test and deploy through a pipeline. If your paper names other principles, the method is the same.

Answer sheet: architecture rules of thumb for an inventory system 10 marks

Architecture rules of thumb

DevOps asks architecture for small changes deployed often, with high confidence. Three rules of thumb support that.

1. Separation of concerns. Consider different aspects of the system separately, each with a specific responsibility. For an inventory system: user interface (stock screens), business logic (adding, removing, reordering stock), database (items, suppliers, stock levels), security (authentication and authorisation), logging (activity and errors) and monitoring (health and performance).

2. Cohesion. The degree to which the elements of a module belong together. It should be high. E.g. a reorder module handles only reordering, as a SpellChecker only checks spelling.

3. Coupling. The degree of dependency between modules. It should be as low as possible. E.g. the reporting module reads stock through an interface and does not depend on how the stock module stores data.

Key insight: high cohesion plus low coupling is separation of concerns, and vice versa. A monolith where everything is tangled has low cohesion and high coupling, so even a small change needs a full redeploy.

Benefit: the stock UI can be changed and deployed on its own life cycle in minutes, without touching the backend.

Modularity, information hiding and types of cohesion

MinorNot asked yetAbout 10 minSyllabus 3.1

Skim this. It is a short extension of lesson 3, and it introduces the running example, Matangle.

Meet Matangle

A SaaS provider that sells access to educational games for school children. Like any such provider, it holds a database of customer information. The module uses this system to build up its architecture story.

Modularity has a sweet spot

  • More modules mean smaller, cheaper individual pieces.
  • But more modules mean more effort spent integrating them.
  • The total cost curve has a minimum around a right-sized number. We cannot predict the number exactly, so avoid both extremes.
  • Example: splitting Matangle's database layer into 50 tiny services would cost more than it saves.

Information hiding

  • Each module hides its own design decisions from the others.
  • Other modules see only what they truly need.
  • Errors made during changes are less likely to spread elsewhere.
  • Example: the customer database exposes one lookup API, never its internal schema.

Common types of cohesion

Functional

One targeted computation, then a result is returned. E.g. a TaxCalculator: give it an order, get back a tax total.

Layer

A higher layer uses a lower layer, never the reverse.

Communicational

All operations act on the very same data.

Check yourself

"All operations act on the very same data" is which type of cohesion?

Functional is one targeted computation; layer is higher uses lower.

Monolithic vs three-tier vs microservices

CriticalAsked: the base of the scenario questions (Oct 2022, Oct 2025)About 30 minSyllabus 3.1

Your second Module 3 deck compares the three styles using one e-commerce application with six functions: product catalog, shopping cart, user authentication, payment, order management, notifications. The same six functions are built three ways. This table is the most reusable thing in Module 3.

The three styles

1. Monolithic

  • All six functions in one project, one process, one shared database, one deployment unit.
  • Any change, even to notifications, needs a full redeploy.
  • Example stack: Django + PostgreSQL.

2. Three-tier

  • Presentation: React or Angular UI.
  • Application: Node.js or Django business logic.
  • Data: PostgreSQL or MySQL, one shared database.

3. Microservices

  • An API gateway in front of six services, each with its own database.
  • Services talk through an event bus or message queue (Kafka, RabbitMQ).
  • Each service can be its own three-tier system.

AspectMonolithicThree-tierMicroservices

Pros and cons

AdvantagesDisadvantages
MonolithicSimple to build; easy end-to-end testing; no network latency between modules; one artifact to deploy; fine for small teams and MVPsCan only scale the whole app; one bug in notifications can crash the store; slower deploys as it grows; locked tech stack; hard for large teams to work at once
Three-tierClear separation of UI, logic and data; frontend and backend teams work independently; backend scales separately from UI; DB changes do not affect the frontend directlyThe backend is still one large block; a payment bug can break the whole backend; cannot pick a different DB for different needs; not ideal at very large scale
MicroservicesScale only what is needed (payment during a sale); independently deployable; different teams own different services; mixed technologies; one service failing does not crash the storeComplex setup (gateway, service discovery); network latency adds up; distributed tracing and debugging are hard; more DevOps effort (Docker, Kubernetes); data consistency across databases is tricky

When to use which

Monolithic

  • Proof of concept.
  • Team under 5 developers.
  • Limited budget and time.
  • Not for high-traffic stores.
  • E.g. a local boutique going online.

Three-tier

  • Separate UI and backend teams.
  • Moderate scalability.
  • Established mid-size store.
  • Not ideal for millions of daily users.
  • E.g. a regional retailer.

Microservices

  • High scale, such as Black Friday spikes.
  • Independent teams per domain.
  • Frequent, safe deployment.
  • Overkill for small or simple stores.
  • E.g. Amazon, Flipkart, Netflix-scale.
Two sentences to close any comparison answer

There is no universal winner: each style fits a team size, traffic level and business need. Complexity grows from monolith to three-tier to microservices: each step adds flexibility and operational overhead. Most platforms (Amazon, Netflix) started monolithic and migrated to microservices as they scaled.

Answer sheet: compare monolithic, three-tier and microservices architectures with an example 10 marks

Monolithic, three-tier and microservices (e-commerce example)

Take an e-commerce application with catalog, cart, authentication, payment, orders and notifications.

  • Monolithic: all functions in one codebase, one process, one shared database, one deployment unit. Simple to build and test, but any change needs a full redeploy, the whole app scales together and one bug can crash everything. Best for MVPs and small teams.
  • Three-tier: separates presentation (React), application logic (Node.js or Django) and data (PostgreSQL). Frontend and backend teams work independently and the backend scales alone. But the backend is still one block and a payment bug can break it all. Best for mid-size applications.

Three-tier systems: Matangle's customer database

CriticalAsked: Oct 2022 (Result Automation System, part a)About 15 minSyllabus 3.2

A classic three-tier, CRUD system, a pattern used for decades. CRUD = Create, Read, Update, Delete.

Presentation tier React frontend: a set of JavaScript and static HTML files
API calls (JSON over HTTP)
Logic tier Clojure on the Java platform (common in larger organizations)
SQL queries
Data tier PostgreSQL, a robust relational database

The catch: tiers tangle back together

  • On paper, each tier should deploy on its own, so small changes propagate easily.
  • In practice, the data and logic tiers often end up tightly coupled. The presentation and logic tiers can tangle the same way.
  • Without lean interfaces, you rebuild the monolith by accident.
  • Example: a Clojure change that also touches PostgreSQL-specific SQL now needs both tiers redeployed together.
Exam line

Three-tier gives separation of concerns (UI, logic, data). To keep the benefit, keep the interfaces between tiers lean, so that low coupling is real, not just on paper.

Answer sheet: three-tier architecture of a result automation system about 4 marks

Three-tier architecture of a Result Automation System

A result automation system takes marks, computes results and shows them to students. A three-tier design separates it into:

  • Presentation tier: web pages where teachers enter marks and students view results (for example React).
  • Logic tier: the backend that validates marks, calculates totals, grades and ranks, and applies rules (for example Clojure, Java or Django).
  • Data tier: the relational database (for example PostgreSQL) storing students, subjects, marks and results.

The tiers communicate through JSON over HTTP (frontend to backend) and SQL (backend to database). It is a CRUD system: create, read, update and delete records.

Benefit: each tier can be changed independently, so the UI can be updated without touching the logic. Caveat: the logic and data tiers can become tightly coupled, so keep interfaces lean.

Database migrations and rolling upgrades

CriticalAsked: Oct 2022 (upgrade the database without downtime, part b)About 25 minSyllabus 3.2

The Oct 2022 question needs two ideas: why databases are different from binaries, and how a rolling upgrade changes the schema with almost no downtime.

Databases aren't like binaries

  • Upgrading a binary: stop it, replace it, start it. State lives elsewhere.
  • A database holds comparatively little logic but a huge amount of state.
  • A schema change is a command that changes structure, not just code.
  • Before and after a change, treat the schema as two different versions.
  • Swapping an app binary loses nothing; swapping a schema carelessly can lose real customer data.

How migration tools track versions

  1. Add a table to the database that stores the current schema version.
  2. Bundle change commands into versioned changesets.
  3. The tool checks the metadata table and runs whatever changesets are missing.

Liquibase

XML changesets.

Migratus

For the Clojure ecosystem.

Flyway

SQL files or Java classes.

Rolling upgrade: splitting the name field

Starting point: one database, two app servers, one load balancer in front. Goal: change the schema and the servers with little to no user-visible downtime. Example: Matangle must split the "name" field into first name and surname, an incompatible change.

StepWhat happensUsers see
1Migrate the DB: add first and last name fields and fill them from the old name field. This is backward compatible, since the old field stays.No change; both servers still use the old field
2Take server two out of the load balancer pool. Server one keeps working with the old field.Service continues on server one
3Upgrade server two to use the new fields, then bring it back online.Service continues; server two is on the new version
4Swap: take server one out, upgrade it too, then restore both servers to the pool.Both servers upgraded
1. Migrate DB (add new fields)→2. Pull server 2 out→3. Upgrade server 2, return it→4. Upgrade server 1, restore both

Only the last, unused old "name" field remains to be dropped. The risky part is already done. The trade: rolling upgrades add extra steps but give near-zero downtime.

Not in your slides

This pattern has a standard name: expand, migrate, contract. Expand = add the new fields (step 1). Migrate = move servers over (steps 2 to 4). Contract = drop the old field later. The slides do not use these words, but they describe the same thing, so one line with the names can earn an extra mark.

Answer sheet: upgrading the database without downtime about 4 marks

Upgrading the database of a Result Automation System without downtime

A database is not like a binary. A binary can be stopped, replaced and started, with state kept elsewhere. A database holds a huge amount of state, so a careless schema change can lose real data. Therefore treat the schema as two versions, before and after, and use a migration tool (Liquibase, Flyway or Migratus) that stores the current schema version in a table and applies versioned changesets.

Rolling upgrade (one database, two application servers, one load balancer). Example: split the student "name" field into first name and surname.

  1. Migrate the database: add the new fields and fill them from the old one. The old field stays, so it is backward compatible.
  2. Remove server two from the load balancer; server one keeps serving using the old field.
  3. Upgrade server two to use the new fields and bring it back online.
  4. Swap: remove server one, upgrade it, and restore both servers to the pool.

Users see almost no downtime. The old field is dropped later.

Delivering features faster with microservices

Split the logic tier of the three-tier system into several small services, such as marks entry, result calculation, notification and report generation. Each service:

  • is small and standalone, so it is easy to build, test and deploy on its own;

Conway's Law: team structure shapes architecture

CriticalAsked: Oct 2025 (e-commerce company with separate teams)About 20 minSyllabus 3.2

The law

"Organizations design systems that reflect their own communication structures." Melvin Conway, 1968.

Three-tier mirrors the traditional IT department

DBA team→Backend team→Frontend team→Operations team

The classic three-tier pattern often mirrors four common IT department teams: a DBA team (data tier), a backend team (logic tier), a frontend team (presentation tier) and an operations team. Each team hands work to the next, so the system gets built in the same layers.

Cross-functional teams and microservices

  • DevOps' core goal is bringing roles together in cross-functional teams.
  • If Conway's Law holds, that team shape gets mirrored in the design.
  • The microservice pattern happens to mirror a cross-functional team closely: one team owns a whole service end to end.
  • Want a certain architecture? Shape the team that will build it first.
  • Example: a single team owning payments end to end naturally ships one clean payments service.

The e-commerce example

Orders team→Order service
Inventory team→Inventory service
Shipping team→Shipping service

Because each team is independent, the software naturally becomes independent microservices too.

DevOps, architecture and resilience

MajorNot asked on its own yetAbout 15 minSyllabus 3.2

The last part of the module. The idea: faster delivery with more moving parts means more places to fail, so you need monitoring and automated action.

Faster delivery, more moving parts

  • Goal: put new features in users' hands faster. Microservices help.
  • But we want fast deploys and reliable software at the same time.
  • More services mean more integration points, so statistically some service failing becomes more likely.
  • Example from the slides: ten small services, each 99.9% reliable, are together less reliable than one monolith at 99.9%. (The maths: 0.999 to the power 10 is about 99.0%.)

Testing isn't enough: you also need eyes on it

  • Automated testing makes sure what you deploy is good quality.
  • It does not help when a healthy service suddenly stops working later. Example: a well-tested service fails at 3am from a full disk.
  • Mitigation: monitoring, plus automated action when something fails.

Resilience in practice: the two-server example

  1. Two application servers run the same application.
  2. The app exposes a special monitoring interface over JSON REST.
  3. A monitoring daemon polls that interface periodically.
  4. If a server fails, the load balancer pulls it from the pool automatically.
Monitoring daemon polls both servers→Server fails→Load balancer pulls it from the pool→Users keep being served by the other server

Why not just monitor CPU and memory?

  • Infrastructure checks confirm the server is up, with CPU, disk and memory to spare.
  • That is not the same as confirming the service works. A service can be "up" with a silently broken database connection.
  • A health probe actively checks that connection and reports the real status.
  • Agree one organization-wide probe response format, so every team's monitoring tool understands it.

Last-hour sheet

Read this just before the exam

Requirements
Functional = what the system does. Non-functional = how well (performance, security, availability), with numbers.
DevOps demand
Deploy small changes often; high confidence; rare rollbacks.
Monolith story
One typo means rebuild and redeploy everything. No modularisation from a deployment point of view. The fix: deploy the frontend component on its own.
Rules of thumb
Separation of concerns (UI, logic, database, security, logging, monitoring). Cohesion high, coupling low. High cohesion + low coupling = separation of concerns.
Modularity
Sweet spot, not too few or too many modules. Information hiding. Cohesion types: functional, layer, communicational.
Three styles
Monolithic: one codebase, one DB, full redeploy, for MVPs. Three-tier: UI, logic, data; one shared DB; backend redeploy. Microservices: many services, own DB each, per-service deploy and scaling, fault isolated; costs: complexity, latency, debugging, consistency.
Three-tier
React, Clojure, PostgreSQL. CRUD. Tiers tangle if interfaces are not lean.
Database migration
Databases hold state. Versioned changesets in a metadata table: Liquibase (XML), Flyway (SQL/Java), Migratus (Clojure).
Rolling upgrade
1. Migrate DB (add new fields, keep old). 2. Pull server 2. 3. Upgrade it and return it. 4. Swap and upgrade server 1.
Microservices
Split the logic tier; REST/JSON; data tier shared (common) or separate. Each can be its own three-tier system.
Conway's Law
Systems mirror the communication structure of the organization. Three-tier mirrors DBA, backend, frontend, ops. Microservices mirror cross-functional teams. Shape the team first.
Resilience
More services means more failure points. Monitoring plus automated action. Health probe, not just CPU and memory. Load balancer pulls failed server.
