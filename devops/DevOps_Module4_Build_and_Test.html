4.1

Build process and Jenkins

A build turns source code and its dependencies into a usable output. The Jenkins example shows how a build server runs a pipeline from the repository through compilation, testing, packaging, publication and deployment. The Jenkinsfile defines the stages. An agent executes the work and the pipeline publishes results such as JUnit XML.

Stage What to write in an answer
Resolve dependencies Maven reads declared dependencies and resolves transitive ones. The local cache avoids redundant downloads.
Build and test mvn clean verify builds and tests the service. Jenkins collects Surefire XML so test results are visible. Failures stop the release path.
Package Produce the application JAR. In the example it is a Spring Boot fat JAR.
Build the image Docker packages the app and runtime. Tag the image with the build-derived version, such as 1.4.42.
Publish the artifact Push the image to Nexus. A retained, versioned image can be pulled again for deployment or rollback.
Deploy Update the Kubernetes Deployment to use the published image. The related pipeline example checks readiness during rollout.

Continuous integration and continuous delivery

  • Continuous integration (CI) merges small changes frequently and automatically builds and tests them. In the teacher’s CI example, compilation, unit tests and a static security scan give early feedback and block a merge if checks fail.
  • Continuous delivery keeps changes ready to release. CI success can trigger automatic staging deployment and integration or smoke testing. A human gate can approve production.
  • Continuous deployment sends passing changes to production automatically. The slides illustrate automated production releases with canary or blue-green strategies, health monitoring and rollback.

For 10 marks on Jenkins and CI/CD. Start with the role of the server and the agents. Draw the staged pipeline. Name the trigger, the test results, the versioned artifact and the production approval point. Explain how those steps enforce both fast feedback and safe delivery.

4.1

Dependencies and the final artifact

A direct dependency is declared by the project. A transitive dependency is required by one of those dependencies and fetched automatically. A development or test dependency supports validation, such as pytest, and stays outside the production package. Keep direct dependencies small to limit compatibility conflicts.

Ecosystem Declaration Typical command Cache or version control
EcosystemMaven (Java) Declarationpom.xml Typical commandmvn dependency:resolve Cache or version control~/.m2/repository, Maven Central
EcosystemGradle (Java, Kotlin, Android) Declarationbuild.gradle Typical commandgradle dependencies Cache or version control~/.gradle/caches, Maven Central or custom repositories
Ecosystemnpm / Yarn (JavaScript) Declarationpackage.json Typical commandnpm install Cache or version controlnpm registry and a lockfile such as package-lock.json
Ecosystempip / Poetry (Python) Declarationrequirements.txt in the pip example Typical commandpip install -r requirements.txt Cache or version controlPyPI, pip cache, or Poetry lockfiles

Resolve conflicts. Maven chooses the nearest version in the dependency tree, and an explicit version can override it. Gradle can apply a strict version constraint. Exclude an unwanted transitive library where appropriate. A Bill of Materials (BOM) aligns related versions, as in the Spring Boot example. Cache dependencies across Jenkins builds to avoid fetching them repeatedly.

Artifact types and versioning

A build artifact is an output of the CI build that can be stored, versioned and deployed. Examples from the deck include a JAR with Java classes and resources, a WAR for a web application server, a Docker image with app and runtime, an npm package, a Python wheel and a native binary.

Version Exam wording
2.5.1 Semantic versioning uses major for incompatible changes, minor for backward-compatible features and patch for backward-compatible fixes.
2.5.1-SNAPSHOT Mutable development version. The same identifier can refer to newer content.
2.5.1 release Stable release. Keep it immutable so a version can be retrieved reliably.
myapp-2.5.1-42.jar Jenkins build number 42 identifies the build for tracing, audit and rollback.

Nexus and Artifactory can store packages in several ecosystems. AWS ECR is used for container images. GitHub Packages fits teams already using GitHub. A repository preserves published outputs for later retrieval.

4.2

Host server, build agents and host software

The host server is the physical or virtual machine supplying CPU, memory and storage. The slides use a Kubernetes cluster to distinguish three roles.

Node role What runs there Operational task
Node roleControl plane What runs thereAPI server, etcd, scheduler and controller manager Operational taskKeep the control plane available.
Node roleWorker What runs thereKubelet, container runtime and application pods Operational taskMonitor capacity and right-size workloads.
Node roleDedicated build node What runs thereJenkins agent or GitLab runner Operational taskIsolate build load from production workloads.

The build agent (called a build slave in the syllabus) executes pipeline jobs scheduled by the CI controller. Agents can run on bare metal, virtual machines, Docker-in-Docker or Kubernetes pods. A pod agent can start on demand, run the job and terminate. The slide example has Jenkins assign an idle agent after a push. The agent checks out code, compiles, tests, builds an image, pushes it to the registry and notifies the team.

Software layers, bottom to top

  1. Hardware or VM. CPU, RAM, storage and network interface.
  2. OS and kernel. Linux namespaces isolate processes, networks and mounts. cgroups control resource use. eBPF supports tracing and networking. Systemd manages services such as kubelet and the container runtime.
  3. Container runtime. Pulls images and starts containers. Kubernetes calls the runtime through CRI. The slides give containerd and CRI-O as examples and distinguish using Docker to build images from using a Kubernetes node runtime.
  4. Kubelet and kube-proxy. Kubelet reconciles desired and actual pod state, calls the runtime, applies pod settings, runs probes and reports status. kube-proxy handles service traffic in the slide architecture.
  5. Monitoring stack. Node Exporter exposes host metrics, cAdvisor exposes container metrics, Prometheus scrapes and stores metrics, and Grafana displays them.
Failure Likely cause and response
OOMKilled Container exceeded its memory limit. Inspect usage and right-size the limit.
CPU throttling Container hit its CPU quota. Adjust the limit or spread load across replicas.
Agent offline Check the agent process, logs and network connection.
ImagePullBackOff Verify registry reachability, DNS and image-pull credentials.
Node NotReady Investigate kubelet and host issues such as disk pressure.

4.2

Triggers, job chaining and build phases

A trigger starts the pipeline. A job chain controls what runs once the pipeline has started.

Trigger Example
Push / SCM change A push to a monitored branch starts a build. A Git webhook can notify the CI system directly.
Schedule Run nightly regression at 02:00 with 0 2 * * *.
Webhook A GitHub pull-request merge can send an event to start a pipeline.
Manual or API A user starts a run or supplies parameters through the CI API.
Upstream job Jenkins can trigger a downstream build after a named upstream job.

Jenkins examples use pollSCM("H/5 * * * *") for periodic polling for repository changes, cron("0 2 * * *") for a scheduled build, and upstream('unit-tests') for an upstream trigger. Polling and receiving a push webhook are two distinct ways to react to SCM changes.

Dependency Meaning Example
DependencySequential MeaningA downstream job waits for its predecessor to pass. ExampleCompile → test → package.
DependencyParallel fan-out MeaningSeveral jobs start from a common predecessor. ExampleRun tests on Linux and Windows.
DependencyFan-in / join MeaningOne job waits on several prerequisite jobs. ExampleDeploy waits for unit tests, lint and the image build in the slide diagram.
DependencyConditional MeaningA job runs only when its condition is true. ExampleDeploy only from main.

A stage groups related jobs. An approval gate can require a human decision, and a quality gate can test a threshold automatically. An artifact carries an output forward. A rollback restores the previous deployment when post-release checks fail.

Phase Output or evidence
Source Latest source-code workspace checked out from version control
Compile Built Java classes or binaries, depending on the project
Test Test results and coverage
Analyse Static security scan, dependency check or quality-gate result
Package Deployable artifact such as a Docker image or Helm chart
Deploy Running application or service in the target environment

4.2

Quality measures and build status

Collating quality measures brings relevant test, security, performance and build data together for each run. Test runners give pass rates and coverage. Static analysis finds code smells and blocker issues. Security and dependency scanners identify vulnerabilities, and load tests measure latency and resource use. The deck names JUnit, SonarQube, Snyk or OWASP tools, and k6 or JMeter.

Example rule in the slides Failure action
Test coverage at least 80% Block merge.
Zero new blockers Block merge.
Zero critical CVEs Block deployment.
Build under 15 minutes Alert and log.

Ways to show build status

View Why use it
Build badge Shows a quick pass, fail, pending or unknown status on the project page.
Pipeline stage view Shows which stage ran, failed or is waiting, with duration and logs.
Build radiator Shared wall display showing the health of builds across the team.
Metrics dashboard Trends over time such as build time, success rate, coverage and flakiness.
Notifications and audit reports Send timely failure messages and record who triggered a run, when and with what result.

4.2

Robustness in CI/CD

A robust pipeline and service keep working through failures or recover safely. The slides group the work into pipeline robustness (retries, timeouts and agent failover), service robustness (health checks, replicas and circuit breakers), rollback (restore a known-good release) and observability (alerts, synthetic monitors and SLOs).

  • Flaky tests pass or fail without a code change. Causes include race conditions, shared state, external services and contention. Retry transient failures within a limit, quarantine known flaky tests, and investigate when flakiness rises.
  • Health probes. Liveness checks whether a container is alive and can trigger a restart. Readiness checks whether it should receive traffic. Startup probes allow time for a slow-starting app before the other probes take effect.
  • Automatic rollback. Restore a previous Helm revision, undo a Kubernetes rollout, switch blue-green traffic back, or let Argo Rollouts revert when metrics breach a threshold.
  • Timeouts, concurrency and failover. Bound run and stage durations. Limit competing deployments to the same environment. Let a compatible agent take over after infrastructure failure.

4.3

Manual testing and test automation

Manual testing still matters for exploratory work, usability, accessibility and visual judgment. The deck recommends trying a test manually before automating it. Automation supports continuous delivery by running repeatable checks at commit time and making failures visible immediately.

Advantage Limitation
Earlier defect detection and better software quality Low-value tests can give false confidence.
More confidence in a release Realistic integration test environments are hard to create.
Less repetitive manual work Tests must evolve with the code.
Repeatable runs and faster verification for CD Environment, timing and shared state can make tests unreliable.
Results collated in readable reports Good tests require skill and ongoing maintenance.

A unit test exercises a well-defined part of the application in isolation. Build tools can run unit tests as part of the pipeline. In the Maven example, test sources live in src/test/java, Surefire discovers conventional test names such as OrderServiceTest and reports to target/surefire-reports/.

4.3

JUnit, Mockito and test coverage

JUnit term Meaning
Runner Starts test execution. The Maven example uses Surefire.
Test case Individual test method marked @Test in JUnit 5.
Fixture Known starting state. @BeforeEach sets it up, and @AfterEach restores or cleans it up.
Suite Groups test classes or test cases to run together.
Execution Locates tests, creates fixtures, runs tests and collects results.
Formatter Produces readable output or XML for Jenkins.
Assertion Checks expected behaviour. Examples include assertEquals, assertTrue, assertNotNull, assertThrows and assertAll.

Mocking supplies a simulated dependency to isolate the unit under test. The deck illustrates a JSON middleware component that normally accesses a database. Unit tests can simulate the database and run without waiting for a live instance. Mockito provides mock() to create the test object, when(...).thenReturn(...) to define a stubbed result and verify() to check an interaction. A spy wraps a real object so selected behaviour can be overridden.

PaymentService pay = mock(PaymentService.class);
when(pay.charge(29.99)).thenReturn(true);
// After exercising the order service:
verify(pay, times(1)).charge(29.99);

Coverage measures how much application code the tests execute. The slides describe Cobertura instrumenting compiled Java bytecode, running tests, and recording which areas executed. A report can show line and branch coverage. JaCoCo and Cobertura are Java examples, Istanbul/NYC is for JavaScript, and Coverage.py is for Python. 100% is an ideal mentioned in class. The separate quality-gate example uses an illustrative threshold of 80%.

4.3

Complete test automation scenario

The teacher’s Matangle example is a user database application. Its layers are the web frontend, JSON/REST interface, application backend and database. The test phases below follow the slide order.

  1. JUnit and Mockito for backend unit tests. Mock UserRepository and EmailService. On successful registration, check that the user is saved and a welcome email is triggered. Test duplicate email and null input as exception cases.
  2. Selenium for the frontend. Run functional tests against the web UI.
  3. soapUI for the service interface. Run functional checks against the JSON/REST interface.
  4. Coverage and deployment decision. Review the unit-test coverage report. The lecture example shows 98% line coverage and 95% branch coverage overall. Mocked dependencies are shown as N/A in that example. All phases must pass before the stack is considered healthy enough to deploy.

For 10 marks. Draw the four layers and the sequence. Name the tool, target layer and success criterion for each phase. For a question framed around a different application, carry over the test-layer structure and choose examples that match the question.
