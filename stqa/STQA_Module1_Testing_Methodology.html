Error, fault, failure and friends

CriticalAsked: Sep 2024About 20 minSyllabus 1.1

These words describe one chain of events. A person slips, the slip sits in the product, and a run exposes it.

TermMeaning (from your slides)
ErrorA mistake made by a team member in any SDLC phase: a typo, a misread specification, a misunderstanding of what a subroutine does. The general word for human mistakes.
Fault / defect / bugA condition that actually causes the system to produce a failure.
FailureThe inability of a system or component to perform a required function according to its specification.
Test caseA well-documented procedure to test a feature. It has an identity, a set of inputs and the corresponding expected outputs. Its purpose is to find errors.
Test oracleThe means to judge whether a test passed or failed, that is, to judge the correctness of the system for that test.
TestwareDocuments produced during testing: test plans, specifications, test case designs, reports.
IncidentThe symptom(s) of a failure that alert the user that a failure has happened.

One example that covers all of them

Requirement: add(a, b) must return a + b. The programmer types return a - b;.

Error
The programmer's slip: typing - instead of +.
Fault
The statement return a - b; sitting in the code.
Failure
add(3, 2) returns 1 when the specification says 5.
Test case
TC-01: input a = 3, b = 2; expected output 5.
Test oracle
The specification "a + b" (or a calculator). It says 5, the program gave 1, so the test fails.
Incident
The user or tester sees a wrong total on screen.
A fault can hide

add(0, 0) returns 0 with the bug and without it. The fault exists but no failure appears. This is why test cases must be chosen carefully, and it leads straight into Module 2.

What a test case looks like on paper

Your slide shows a template with these fields: test scenario ID, test case ID, description, priority, pre-requisite, post-requisite, then one row per step with action, inputs, expected output, actual output, test result (pass or fail) and comments.

Answer sheet: define failure, fault, error, test case, test oracle with an example 10 marks, about 2 per term

Software testing terminology

Example used throughout: add(a, b) must return a + b, but the code says a - b.

  • Error: a mistake made by a developer in any phase of SDLC. Here, typing - instead of +.
  • Fault (bug, defect): the condition in the product that causes a failure. Here, the statement return a - b.
  • Failure: inability of the system to perform a required function per its specification. Here, add(3,2) gives 1 instead of 5.
  • Test case: a documented procedure with an ID, inputs and expected outputs, used to find errors. Here, TC-01: a=3, b=2, expected 5.
  • Test oracle: the means to judge the success or failure of a test. Here, the specification a + b: expected 5, actual 1, so FAIL.

Chain: error leads to fault, fault leads to failure.

Life cycle of a bug

CriticalAsked: Sep 2024About 25 minSyllabus 1.1

Your slides show this twice: once as two phases (bugs in, bugs out) and once as a list of states. The question usually wants both: "block diagram" and "list the states".

View 1: bugs in, bugs out

  • Bugs-in phase: a human error in any development phase puts a bug into the product, and the bug travels to the next phase if nobody catches it.
  • Bugs-out phase: once testing shows a failure, the team classifies the bug (how serious, which kind), isolates it (which module or line), and resolves it (fix and retest).

Why bugs occur

  • To err is human.
  • Bugs from earlier stages go undetected and propagate into later ones.
  • The cost of debugging rises the longer a bug survives, which is the economic argument for testing early.

Classification by criticality: critical (system unusable or data loss), major (key feature broken), medium, minor (cosmetic).

View 2: the states

StateWhat it means
NewA tester has just reported the bug. Nobody has confirmed it yet.
OpenThe bug is confirmed as genuine.
AssignThe bug is given to a developer or team to fix.
DeferredThe bug is real, but the fix is postponed to a later release (low priority or no time).
RejectedNot a genuine bug: invalid, duplicate, or cannot be reproduced.
TestThe developer has fixed it and handed it back to the tester for retesting.
Verified / FixedThe tester retested and the fix works.
ReopenedThe bug still appears after the fix, so it goes back to the developer. Your slide lists this state as "Responded".
ClosedThe bug is verified as fixed and the report is closed.

Goals of software testing

CriticalAsked: Sep 2023, Sep 2025About 25 minSyllabus 1.1

Start from the definition, because every goal flows from it: testing is the process of executing a program with the intent of finding errors. A successful test is one that uncovers an as-yet-undiscovered error. Testing can show the presence of bugs but never their absence.

The three groups of goals

Immediate goals

  • Bug discovery: find errors at every stage of development.
  • Bug prevention: learn from the bugs found so the same mistakes are not repeated.

Long-term goals

  • Reliability: confidence that the software runs without failure.
  • Quality: testing produces reliability and quality.
  • Customer satisfaction: quality leads to satisfied customers.
  • Risk management: reduce the risk of failures reaching users.

Post-implementation goals

  • Reduced maintenance cost: bugs caught before release are cheaper than bugs fixed after.
  • Improved testing process: lessons from this project make the next test process better.
Remember

Immediate: find and prevent. Long-term: reliability, quality, customers, risk. Post-implementation: cheaper upkeep, better testing next time.

Why not test everything?

Complete testing is impossible, so the aim is effective testing rather than exhaustive testing.

  • Too many inputs. Valid inputs, invalid inputs (out-of-range numbers, letters mixed with digits, control characters, any other key), edited inputs, and race-condition inputs.
  • Too many paths. Loops and branches multiply the number of paths through even a small program.
  • So: choose the subset of the domain that matters most for the project's priorities, so the chance of failure in the real environment is as small as possible.
Psychology trap

"Testing demonstrates that there are no errors" is the wrong mindset. Your slide contrasts it with the right one: testing is executing the program with the intent of finding errors.

Answer sheet: categorize and explain the goals of software testing 10 marks

Testing as a process, and the STLC

CriticalAsked: Oct 2022 (STLC), Oct 2025 (process)About 35 minSyllabus 1.1

Two questions, one lesson. "Explain software testing as a process" is the big picture. "Draw the STLC" is the four-phase cycle inside it. Learn the process view first and the STLC becomes its detail.

How testing grew up

  • Testing 1.0: a single phase done after coding.
  • Testing 2.0: testing gains importance in the SDLC and the idea of early testing starts.
  • Testing 3.0: testing becomes a process built on strategic effort, with a roadmap, driven by quality goals so it can be controlled and monitored.

What makes testing a process

The testing process emerged out of development and runs in parallel to it. Its properties:

  • It is organised so that important and critical features get enough time.
  • Techniques are chosen so they detect the maximum number of bugs.
  • Quality factors are quantified, so the process can be monitored and measured.
  • Procedures and steps are defined and documented.
  • There is scope for continuous process improvement.

The model behind it

The STLC: four phases

1. Test planning

  • Define the test strategy. Estimate the number of test cases, their duration and cost.
  • Plan resources: people, tools, documents. Identify risks and set completion criteria.
  • Choose methodologies, techniques and tools. Define reporting, bug classification and severity levels, project metrics.
  • Decide the test case format, which cases to automate, priorities, stress and performance areas, and the test cycles for regression.

2. Test design

  • Set test objectives and priorities. List the items to be tested.
  • Map items to test cases: find the major scenarios, remove redundant cases, add cases for objectives that have none.
  • Select design techniques, create test cases and data, set up the test environment and tools, write the test procedure specification.
  • Rule: cover all features, but do not create too many test cases.
A good test case

Is designed around critical, high-risk requirements. Has a high chance of finding an error. Does not overlap other cases. Is simple, reusable and recombinable. Is most likely to find an as-yet-undiscovered error.

3. Test execution

Run the cases and produce three documents: the test incident report, the test log and the test summary report. Who executes depends on the level:

LevelPerson responsible
UnitDeveloper of the module
IntegrationTesters and developers
SystemTesters, developers, end-users
AcceptanceTesters, end-users

4. Post-execution / test review

When the developer gets the bug report: understand the bug, reproduce it, analyse its nature and cause, then do reliability analysis, coverage analysis and an overall defect analysis. The findings feed back into the next planning round.

Answer sheet: draw the STLC and explain briefly 10 marks

Software testing life cycle (STLC)

The STLC is the sequence of testing activities carried out in a defined order alongside development.

Draw the four boxes with the feedback arrow.

  • Test planning: strategy, number and cost of test cases, resources, risks, completion criteria.
  • Test design: objectives, items to test, mapping items to test cases, techniques, test data, environment.
  • Test execution: run cases; produce incident report, test log, summary report.
  • Post-execution: reproduce and analyse bugs; reliability, coverage and defect analysis.

Outputs: strategy and plan, test cases and procedures, bug reports and metrics. Feedback improves the next cycle.

Verification and validation

CriticalAsked: Sep 2025 (verification of high-level design)About 30 minSyllabus 1.2

A test strategy has to start at the component level and finish at the whole system. That gives two ideas which are the basis of all testing: verification, while building, and validation, once there is something to run.

VerificationValidation
QuestionAre we building the product right?Are we building the right product?
ChecksThe product against its specification at every development phase.The software as a whole against customer expectations and the functional design.
HowReviewing documents, design and code without running them.Executing the software: unit, integration, function, system, acceptance tests.
WhenAll SDLC stages up to coding. Its scope shrinks as a module nears completion.Takes over from verification in the later stages. The last chance to find bugs before release.
WhyDefects are found early and do not propagate.Confirms the product satisfies user requirements.

Why verify early

  • Without it, the delivered product can drift away from the required one.
  • It exposes more errors, early decreases the cost of fixing them, and raises quality.
  • Three principles: everything must be verified; results of verification may not be binary; even implicit qualities must be verified.

What is verified at each stage

Requirements (the SRS)

Each requirement is checked for being correct, unambiguous, consistent, up to date, and traceable.

High-level design (HLD)

HLD has three parts, and each is verified:

  • Data design: the data objects, structures and database are described completely, and every data element the SRS needs is present and consistent.
  • Architectural design: the modules and their relationships cover every requirement, nothing is missing, and the structure is modular.
  • Interface design: the interfaces between modules and with users, hardware and other systems are fully and consistently defined.
Where this comes from

The three parts of HLD come from your slide. The checks written under each part are the standard textbook checks, added so you have something to write for 10 marks.

Low-level design (LLD)

Verify the SRS and the design document of every module. Data structures, interfaces and algorithms are shown in design notations, so check that every item is consistent with its notation.

Code (unit verification)

Check the code against these eight points: misunderstood arithmetic precedence, mixed-mode operations, incorrect initialisation, precision inaccuracy, incorrect symbolic representation of an expression, different data types, improper or missing loop termination, failure to exit.

Verification is done with the static techniques of Module 2: inspections, walkthroughs and technical reviews.

Verification of high-level design

Verification asks "are we building the product right?". It checks work against its specification at each phase so defects are caught early.

The HLD converts the SRS into a design of the system. It has three parts, each verified:

  • Data design: data structures and database are complete; all data in the SRS is covered; they are consistent.
  • Architectural design: modules and relationships cover every requirement; modular, nothing missing.
  • Interface design: internal and external interfaces are complete and consistent with the SRS.

Method: inspections, walkthroughs and reviews. The tester also prepares the function and integration test plan at this stage.

Benefit: a design error found here costs far less than one found after coding.

CriticalAsked: Oct 2025About 25 minSyllabus 1.2

The V-model puts verification and validation into one picture. The left arm goes down through development, and at every step the tester builds the test plan that will be used on the right arm. The right arm goes back up, executing those plans.

Your slide also shows an expanded V with the same idea in other words: define specifications pairs with check specifications, design with check design, coding with unit test, integrate with integration and system test.

The point of the V

Testing starts as soon as the SRS is prepared, not after coding. The tester performs verification and prepares a test plan during every SDLC phase, so test planning is finished before the code exists.

Advantages and limits

Advantages

  • Test planning starts early, so defects are found early.
  • Every development phase has a matching test level, which makes coverage clear.
  • Verification and validation are both built in.

Limits

  • Rigid and sequential. Changing requirements are expensive.
  • No working software until the coding stage.
  • Not a good fit for unclear requirements or iterative projects.

Validation testing: unit, integration, function, system, acceptance

CriticalAsked: Oct 2022 (unit), Sep 2023 (types), Sep 2025 (pair-wise)About 45 minSyllabus 1.3

Validation means running the software. It happens in levels, small to large, and each level matches one test plan from the V-model. Three of your five papers asked something from this lesson, so it is the biggest one in Module 1.

LevelWhat it testsWho
UnitOne module on its own. Needs drivers and stubs.Developer
IntegrationThe interfaces between modules as they are combined.Testers and developers
FunctionEach business function against the requirements.Testers
SystemThe whole integrated system: stress, performance, security, compatibility, recovery.Testers, developers, end-users
AcceptanceWhether the software is fit for the user. Alpha and beta.Testers, end-users

Unit testing

Unit validation testing checks one module in isolation before it is combined with others. It is done by the developer, who knows the code. The difficulty: a unit usually calls other units that are not ready, and nothing is calling it yet. Drivers and stubs fill those gaps.

Driver
A module that invokes the module under test: it supplies test inputs, controls and monitors execution, and reports results. In its simplest form it is a line of code that calls a method and passes a value.
Stub
A stand-in for a subordinate unit that the unit under test calls. Much simpler than the real unit: it does nothing of its own, may print a trace message, and returns a constant or null. It can also simulate exceptions.

Worked example from your slides

main() reads three numbers and calls calsum, caldiff and calmul.

int calsum(int x, int y, int z) {
    int d;
    d = x + y + z;
    return d;
}

(a) main() is not ready, but we want to test calsum(). Write a driver that stands in for main():

main() {
    int a, b, c, sum;
    scanf("%d %d %d", &a, &b, &c);
    sum = calsum(a, b, c);
    printf("The output from calsum module is %d", sum);
}

(b) caldiff() and calmul() are not ready when we test main(). Write stubs:

caldiff(int x, int y, int z) {
    printf("Difference calculating module");
    return 0;
}
calmul(int x, int y, int z) {
    printf("Multiplication calculation module");
    return 0;

Integration testing

After units pass, modules are combined and the tests look at the interfaces between them: data passed, calls made, results returned. Your slide groups the approaches into three families.

Decomposition-based: top-down and bottom-up

Modules form a tree by functional decomposition. Top-down starts at the main module and adds lower modules step by step, using stubs for the ones not yet added. Bottom-up starts with the lowest modules and moves up, using drivers for the callers not yet added.

IssueTop-downBottom-up
Architectural designErrors in high-level design are found at an early stage.High-level design is validated at a later stage.
System demonstrationThe system grows from top to bottom, so feasibility can be shown to top management early.Feasibility may not be demonstrable early, unless some modules are reusable.
Test implementation(nodes − 1) stubs are needed for subordinate modules.(nodes − leaves) drivers are needed for super-ordinate modules.

Call-graph-based: pair-wise and neighbourhood

Draw a call graph: each module is a node, each call is an edge. Then integrate along the edges instead of along a tree.

  • Pair-wise integration: every edge, that is every pair of modules where one calls the other, is tested together as one session. Only those two real units run. Everything else is left out or stubbed. Number of sessions = number of edges.
  • Neighbourhood integration: one node plus all its immediate callers and callees are tested together.

Path-based

Tests follow execution paths that cross module boundaries, instead of the structure of the call tree.

Pair-wise example: an online order system

Order calls Cart and Payment. Cart calls Inventory. Payment calls Gateway.

SessionUnits tested togetherWhat the test checks
S1Order + CartOrder passes the item and quantity; Cart returns the updated total.
S2Order + PaymentOrder passes the amount; Payment returns success or failure.
S3Cart + InventoryCart asks for stock; Inventory returns available or out of stock.
S4Payment + GatewayPayment sends the card request; Gateway returns approved or declined.

Why it is useful: no big scaffolding of stubs and drivers is needed, and a failure points at one pair of modules, so it is quick to isolate. Its cost: more sessions than a top-down or bottom-up pass over a small tree.

Function testing

Measures the quality of the functional (business) components of the system. It checks that the system behaves correctly from the user's or business's point of view, according to the requirements. Each component or business event must:

  1. perform in accordance with the specifications,
  2. respond correctly to every condition that incoming events or data can create,
  3. move data correctly from one business event to the next, including data stores,
  4. be initiated in the order needed to meet the business objectives.

Sanity testing

Not in your slides

Sanity testing is listed in syllabus 1.3 but the slides skip it, so this is the standard definition. A sanity test is a quick, narrow check, done on a new build or after a small fix, that the changed or most important functions work. If it fails, the build goes back to the developers and deeper testing does not start. Its broad, shallow cousin is the smoke test: does the build run at all?

System testing

Tests the fully integrated system against the system requirements before it is handed over for acceptance. It includes several kinds of testing:

  • Stress: push the system beyond its normal load or limits.
  • Performance: speed, response time, throughput.
  • Security: protection against unauthorised access.
  • Compatibility: works across operating systems, browsers, hardware.
  • Recovery: the system recovers after a crash or failure.

Acceptance testing

Designed to decide whether the software is fit for the user, to make users confident in the product, to check it against the acceptance criteria, and to let the buyer decide whether to accept it.

Alpha testingBeta testing

WhoEnd-usersEnd-users in their own setting
EnvironmentCan be controlled somewhatDevelopment team has no control

Testing principles and test strategy

MajorNever asked yetAbout 15 minSyllabus 1.1

Read this once. If a short question on principles or strategy turns up, this is enough.

Ten principles of testing

  1. Effective testing, not exhaustive testing.
  2. Testing is not a single phase of the SDLC.
  3. Destructive approach for constructive testing: try to break the software so it can be made better.
  4. Early testing is the best policy.
  5. Error clustering: the chance of an error in a section is proportional to the number of errors already found there.
  6. Start testing at the smallest module and expand towards the whole program.
  7. Testing should also be done by an independent team.
  8. Everything must be recorded.
  9. Invalid inputs and unexpected behaviour have a high chance of finding errors.
  10. Testers must take part in specification and design reviews.

Test strategy

A test strategy has to continue until the project is implemented, and runs from component level to the whole system. It is organised as a matrix of test factors against test phases. To create one:

  1. Select and rank the test factors (for example portability, service level).
  2. Identify the test phases (requirements, design, code, unit test, integration test, system test).
  3. Identify the risks for each factor in each phase.
  4. Plan the strategy for every risk found.

When building the methodology: determine the project risks, determine the type of project, pick test activities for each SDLC phase, then build the test plan. The test plan covers: environment and background, overall objectives, test team, schedule and budget, resources, testing materials, the functions to be tested, and the technique to use in each phase.

The two families of techniques come next, in Module 2: static (no execution) and dynamic (execution, either black-box or white-box).

  • Myths: testing is a single phase; testing is easy; development is worth more than testing; complete testing is possible; testing starts after coding; the purpose is only to check functionality; anyone can be a tester. All false.

  • Effective testing is hard because defects are hard to find and it is hard to say when testing is done.

Last-hour sheet

Read this just before the exam

Chain
Error (human slip) → fault (in the product) → failure (wrong behaviour) → incident (symptom noticed).
Oracle
What decides pass or fail. Test case = ID + inputs + expected output.
Bug states
New, Open, Assign, Deferred, Rejected, Test, Verified/Fixed, Reopened (Responded), Closed. Phases: bugs-in, bugs-out (classify, isolate, resolve).
Goals
Immediate: discovery, prevention. Long-term: reliability, quality, customer satisfaction, risk management. Post-implementation: lower maintenance cost, better testing process.
Process
1.0 single phase after coding; 2.0 early testing; 3.0 strategic process. Five properties: time for critical features, techniques that find most bugs, quantified quality goals, documented procedures, continuous improvement.
STLC
Planning, design, execution, post-execution. Outputs: strategy, test cases, bug reports and metrics. Execution gives incident report, test log, summary report.
V and V
Verification: build it right, static, up to coding. Validation: build the right thing, executes the software.
HLD
Data design, architectural design, interface design.
V-model
Requirements → acceptance plan. SRS → system plan. HLD → function and integration plan. LLD → unit plan. Right arm executes them.
Levels
Unit (driver and stub), integration (top-down needs stubs, bottom-up needs drivers, pair-wise = one edge per session), function, system (stress, performance, security, compatibility, recovery), acceptance (alpha at developer, beta at customer).
