Measurement objectives and GQM

A software metric is a quantitative measure of an attribute of a product, process or resource. Testing teams use metrics to estimate effort, monitor status, find bottlenecks and support decisions such as release readiness.

Goal → Question → Metric (GQM)

Define a goal, ask a question that tells you whether the goal is being met, then choose a measure that can answer the question. Goal. Complete planned regression testing before release. Question. How much of the planned suite is complete? Metric. Completed regression tests divided by planned regression tests, as a percentage.

What can you measure?

A product measure describes the application, such as its functional size. A process measure describes how work happens, such as the average time from reporting a defect to verifying its fix. A resource measure describes the people, time or equipment available, such as tester person-hours.

An internal attribute can be measured from an artifact, such as the lines of source code. An external attribute describes behavior in use, such as response time under load. Define the unit, what to include, when to measure, and what decision the result will inform.

Try GQM for a release with unresolved critical defects.

Goal: reduce critical release risk. Question: how many confirmed critical defects are still open? Metric: count unresolved defects classified as critical at the release review.

Attributes and corresponding metrics

An attribute is what you care about. A metric gives you a number you can record for that attribute. For example, to measure the completeness of testing, count how many in-scope requirements have been exercised and divide by the total in scope.

Use the number to make a decision. For an exit criterion of zero open critical defects, check the count just before release. To assess automation cost, compare the time saved over repeated runs with script setup, maintenance and infrastructure costs. To estimate suite size, count regression cases separately from the tests planned for new features.

Examples of testing attributes and their metrics
AttributePossible metric
ProgressExecution percentage or number of unresolved defects.
CostActual testing cost compared with budget, or testing hours per function point.
QualityDefects per function point or percentage of requirements exercised.
SizeNumber of planned test cases, regression tests or automation candidates.

Four product metrics for a 10-mark answer

  1. Lines of code (LOC) measure implementation size. One team might count 2,000 non-blank, non-comment lines. Comparisons assume consistent counting rules and similar languages.
  2. Function points (FP) measure the size of functionality delivered to users. A count considers inputs, outputs, inquiries, internal logical files and external interface files. Historical rates like testing hours or cost per FP can predict effort or cost for a similarly scoped project. At 3 hours per FP, 100 FP would take an estimated 300 person-hours.
  3. Halstead volume estimates how much information a program’s tokens represent. It uses total token count and operator/operand vocabulary, V = N × log₂(n).
  4. Defect density measures observed defects per size unit, for example 12 confirmed defects in 60 FP gives 0.20 defects per FP. Compare values from a similar test phase and defect scope.

Estimation models for testing effort

Testing effort is the work required, usually measured in person-hours. Duration is the elapsed calendar time, while staffing is the number of people needed to do the work. Choose an estimate based on the information you actually have, then calibrate it using past projects of similar scope.

From effort to staffing

Suppose 80 procedures historically require 160 person-hours. The baseline is 2 hours per procedure. For 120 new procedures, estimate 240 person-hours. If each tester can contribute 60 productive hours in the available window, estimate 4 testers.

For task planning, split a 240-hour estimate into planning (20%, or 48 hours), design (30%, or 72 hours) and execution (50%, or 120 hours). If a new browser matrix adds 20 hours to execution, revise the total to 260 person-hours. Historical splits are starting points. Review the assumptions before using the numbers as commitments.

Choose the model based on what you know
ModelBasis and example
Development ratioUse a developer-to-tester ratio. With 12 developers and a 3:1 ratio, estimate 4 testers.
Project-staff ratioUse the historical testing share of the whole project team. 20% of 30 staff gives 6 testers.
Test procedure methodMultiply the number of planned procedures by historical hours per procedure. 100 procedures × 2 hours gives 200 person-hours.
Task planning methodAllocate effort across activities such as test planning, design and execution using historical splits. Adjust each estimate for the current scope and sum the adjusted hours.

Halstead effort numerical

Halstead measures a module using the operators and operands in its source code. For example, total = price + tax has = and + as operators, with total, price and tax as operands. In an effort-allocation problem, the module with a larger share of total Halstead effort gets a larger share of the testing effort.

Lowercase n counts distinct items. Uppercase N counts all occurrences. Subscript 1 means operators and 2 means operands.

Vocabulary n = n₁ + n₂
Length N = N₁ + N₂
Volume V = N × log₂(n)
Difficulty D = (n₁ ÷ 2) × (N₂ ÷ n₂). Program level PL = 1 ÷ D.
Effort E = V ÷ PL = V × D
Effort share (%) = 100 × E for the module ÷ sum of E for all modules

Worked past-paper problem

For module A, n = 23 + 12 = 35 and N = 43 + 37 = 80. Then V = 80 × log₂(35) ≈ 410.34, D = (23 ÷ 2) × (37 ÷ 12) ≈ 35.4583 and E ≈ 14,550.07. Apply the same steps to the other modules.

Information flow metrics

Information flow metrics measure a module’s interactions so testers can identify modules that may need extra interface and integration testing.

  • Local direct flow. A module passes information to a called module, which can return a result to the caller.
  • Local indirect flow. The caller takes a result from one called module and passes it to another, such as passing a tax calculation to an invoice generator.
  • Global flow. Information passes between modules through a shared data structure.
Fan-in = incoming local flows + data structures read
Fan-out = outgoing local flows + data structures updated

If a module receives two local flows and reads one shared structure, fan-in is 3. If it generates two outgoing flows and updates one shared structure, fan-out is 3. A high fan-in suggests the module receives information from several sources. A high fan-out suggests its outputs or updates can affect several parts of the system. Test those interfaces and shared-state interactions.

What to test when the flow is complex

In a checkout workflow, test a valid and an invalid response from the tax module, then check that the result passed to the invoice module uses the right currency and precision. If inventory and checkout share stock information, verify that an order update is visible to both and that an unsuccessful order leaves the shared stock correct.

One form of the Henry–Kafura measure uses module length × (fan-in × fan-out)². With length 20, fan-in 3 and fan-out 2, the relative measure is 720. Use a consistent definition of length and flows when comparing modules.

Test Point Analysis (TPA)

TPA estimates person-hours for system or acceptance testing from the functional size of the software, the test strategy and the conditions under which the team will work. It supports staffing, scheduling and budgeting before all tests have been designed.

  1. Estimate dynamic test points. Start from each function’s function points. Weight them for factors such as complexity, interfaces, importance and frequency of use, and for the quality characteristics the tests must cover. Sum the points for all functions.
  2. Estimate static test points. Use the system’s functional size and the scope of quality characteristics assessed without running the software, for example through a review checklist.
  3. Convert total points into hours. Add both point counts and multiply by the environment factor and a productivity factor. The result covers primary work such as preparing, specifying, executing and completing tests.
  4. Add the control allowance. Include hours for planning and control. The result is total testing effort in person-hours.

Example with assumed factors. 80 dynamic + 20 static = 100 points. At an environment factor of 1.2 and 0.5 person-hours per point, primary effort is 60 person-hours. With a 10% control allowance, total effort is 66 person-hours.

Testing progress metrics

Progress metrics track how much testing is complete, what results it produced and how much work remains. Review them together because each uses a different denominator or measures a different activity.

MetricHow to measure itWhat it tells you
Execution progressCompleted test executions ÷ planned test cases × 100.Shows schedule progress. Track blocked or unrun tests separately.
Pass ratePassed tests ÷ executed tests with a pass/fail result × 100.Shows the share of completed tests that passed.
Requirements coverageIn-scope requirements exercised by at least one test ÷ all in-scope requirements × 100.Shows which requirements still need to be tested. State whether coverage means designed, executed or passed tests.
Defect backlogCount of unresolved defects at the end of a period. Closing backlog = opening backlog + new + reopened − closed.Compare arrivals with closures and break down open defects by severity and age.

Worked dashboard. 100 planned, 60 executed, 45 passed, and 18 of 24 requirements exercised gives 60% execution, 75% pass rate and 75% requirements coverage. If 12 defects were open, 8 were reported, 2 reopened and 4 closed, the ending backlog is 18.

Model answer for the five-day backlog question

A continuous rise means more defects entered or returned to the open queue than were closed each day, assuming the reporting scope stayed the same. Possible causes include more effective testing, a recent risky change, slow fixes, or delayed verification. Compare daily arrivals and closures, then inspect open defects by severity, age and module. If high-severity items are accumulating, prioritize them and reassess the exit criteria before release. Explain the four metrics above for the second part of the question.

Function point metrics for testing

A function point (FP) measures functional size from the user’s perspective. An FP count classifies and weights the functions users need, so testers can use historical rates independently of the implementation language.

Function typeShopping-site example
External input (EI)Submit a shipping address that updates the order.
External output (EO)Produce an invoice containing a calculated tax amount.
External inquiry (EQ)Look up an order status with no derived calculation or data update.
Internal logical file (ILF)Order records maintained by the shopping application.
External interface file (EIF)Catalogue records read by the app and maintained by a separate system.

Relevant testing measures include hours per FP, cost per FP, FP tested per person-month, defects per FP and test cases per FP. If a similar project took 3 hours per FP, estimate 300 person-hours for 100 FP.

Function-point numerical from the lecture

The lecture gives historical rules of thumb for this example. For 760 FP and 456 defects, estimate total cases as 7601.2 ≈ 2,864, and acceptance cases as 760 × 1.2 = 912. Defect density is 456 ÷ 760 = 0.60 defects/FP. The lecture calls 2,864 ÷ 760 ≈ 3.77 test cases/FP test-case coverage. That ratio has units of cases per FP.

Draw the TPA diagram and distinguish FP from TPA.
