Need for automation

Test automation uses tools or scripts to set up tests, execute them, compare actual results with expected results, and report outcomes. It saves repeated effort, makes regression checks faster, applies checks consistently, and can simulate loads or data volumes hard to reproduce by hand. It frees testers to explore new features and investigate failures.

Manual vs automated testing
AspectManualAutomated
ExecutionA tester follows or explores the workflow and evaluates the outcome.A script executes recorded steps and checks defined assertions.
CostLess setup for a quick check. Effort recurs each run.Requires writing and maintaining scripts. Repeated runs generally cost less in tester time.
Best fitExploratory work, usability judgment and one-off checks.Stable, repeatable regression, many data combinations and load simulation.

Keep a test manual when it is a one-off check, the interface is changing so frequently that upkeep outweighs the savings, or the outcome requires human judgment, as in exploratory or usability testing. For a 5-mark answer, give these reasons with one example.

Guidelines for automated testing

  1. Decide whether to build or buy. Compare custom development with available tools and their total upkeep.
  2. Pilot the tool on a prototype. Use a small representative workflow to verify compatibility and useful reports.
  3. Pick suitable cases. Favor stable, often-repeated scenarios with a clear expected result.
  4. Match organizational needs. Check the technology, test objective, SDLC stage, team skills, budget, schedule and tools already in use.
  5. Develop maintainable scripts. Use reusable actions, independent test data, clear assertions and version control.
  6. Automate regression where feasible. Automate high-impact workflows first, such as checkout totals or login for a test account.

Performance tool for the past-paper question

Apache JMeter is an open-source performance testing tool. In a test plan, a Thread Group represents virtual users, an HTTP Request sampler sends requests, and a results report summarizes response time, throughput and errors. For example, simulate 100 shoppers browsing a catalogue in a test environment. Compare the measured response time and error rate with the agreed targets.

Categorization of testing tools

Tools can be grouped by how they inspect software and by the testing activity they support. Static tools examine artifacts without running the software. Examples include code analyzers that identify unreachable code or uninitialized variables. Dynamic tools gather information during execution, such as statements and branches covered.

Activity categoryTypical support
Reviews and inspectionsCode comprehension, coding-rule checks and complexity analysis.
Test planningPlan templates, scheduling, staffing estimates and scope tracking.
Test design and developmentGenerate candidate cases or data and map them to requirements.
Execution and evaluationBrowser automation, coverage collection, memory checks, pass/fail reports and performance measurement.

Example. In one project, a source analyzer checks the code before execution, Selenium checks a checkout workflow in a browser, and JMeter measures request performance under load. Each supports a different testing objective.

Selection of testing tools

Choose a tool by matching it with the test objective, the SDLC phase, the application stack and the people who will use it. A release team may need tools for different jobs, such as browser checks and load measurement.

  1. Define needs. Specify what to test, which environments to support, and what evidence the tool must produce.
  2. Check fit. Compare platform support, skills, integration with the build pipeline and reporting.
  3. Estimate total cost. Include licenses, runners, training, script development, configuration and future maintenance. Check the schedule and time to learn the tool.
  4. Run a small pilot. Automate a representative checkout flow and compare setup time, reliable reruns and failure reports across candidates.
  5. Decide and review. Select the smallest set that meets the needs, document ownership, and assess whether the tools continue to save time.

Data-driven testing

Keyword-driven testing

Test cases are written as a sequence of named actions called keywords. A driver reads each row, looks up the keyword in an action library, passes in the arguments, and records the result. Test authors compose scenarios from reusable actions. The library contains the code that carries them out.

One login scenario written with keywords
StepKeywordArguments
1OpenPageLogin page
2EnterTextUsername field, test account username
3EnterTextPassword field, valid test password
4ClickSign in button
5VerifyPageAccount dashboard

Benefits. Reuse actions across scenarios, write readable test cases, let domain testers author scenarios with fewer code changes, and update a shared keyword implementation when the interface changes. The team has to build and maintain the driver and library.

Data-driven testing varies inputs and expected results. Keyword-driven testing composes or varies actions. One framework can use both.

Synthetic data generation using AI

Synthetic data consists of artificial records generated for testing. Specify a schema, dependencies and scenarios, then use a tool such as an LLM to create rows. For checkout, request fake product IDs, whole-rupee prices, cart totals around ₹500 and a deliberately invalid row with a missing product ID. Check field types, relationships and boundary coverage. Use mock values and keep the approved dataset versioned for repeatable runs.

  1. Describe the data. Specify required fields, permissible values, and relationships, such as valid product IDs for order lines.
  2. Request useful variation. Include valid, boundary and explicitly invalid cases. Ask for structured output such as CSV or JSON.
  3. Validate before execution. Check the schema, unique identifiers, totals and test coverage. Validate valid and intentionally invalid records against their respective expectations.
  4. Store approved fixtures. Keep reproducible inputs with the tests. Where relevant, preserve realistic distributions while avoiding production records.

Testing web-based systems

A web application involves a browser, network, server and often a database or third-party API. Web testing checks user-facing behavior and the interactions between these components. Challenges include browser and device diversity, different network conditions, third-party failures, concurrent users, rapid releases and frequent changes.

Web testing methods
MethodWhat to verify
InterfaceCheck browser-to-server, server-to-database and service interactions. Verify that failures show a clear error and leave data consistent.
UsabilityCheck whether users can understand labels, complete workflows and recover from mistakes.
ContentCheck static labels and dynamic content, such as product prices and availability.
NavigationCheck internal links, external links, redirects, and search paths. Test Back/Forward and expected routes after redirects.
CompatibilityCheck forms and layouts on supported browser, operating system, screen size and device combinations.
SecurityVerify infrastructure configuration and app controls. Check role permissions, sign-in and sign-out, session expiry, and that sensitive data travels over HTTPS.
PerformanceMeasure response time, throughput, error rate, resource utilization and database load. Load testing uses expected demand. Stress testing pushes beyond normal capacity to observe degradation and recovery.

Web vs desktop. Web testing emphasizes browser and device compatibility, network behavior, shared server capacity, and sessions across requests. Desktop testing typically emphasizes supported OS versions, installation and updates, local files, permissions and hardware. A networked desktop app can share web-system concerns.

Challenges in web testing

Web applications combine a heterogeneous client environment with services spread across a network. A single user action can involve the browser, an application server, a database and an external payment service.

ChallengeExample and testing response
Diversity and compatibilityCheckout looks different across screen sizes. Prioritize frequently used browser, OS and device combinations.
Dynamic environmentNetwork delay or changes in live inventory affect what users see. Test slower connections and use known fixtures when asserting data.
InteroperabilityA payment service can be unavailable. Verify service interactions and exercise error handling with a test double or sandbox.
Short releases and evolutionFrequent updates can break old flows. Rerun critical automated regression cases on each release.
Concurrent usersSeveral shoppers may try to order the last item. Verify correct stock counts and measure behavior under expected demand.

Web security testing

Web security testing verifies infrastructure safeguards and application controls that protect data and functions. Examples include checking that HTTPS is configured, privileged operations require the right role, and sessions are handled securely.

  • Authentication checks identity. A valid test user should be able to sign in, and incorrect credentials should be rejected.
  • Authorization checks what an identified user can do. A test customer should see their own orders. The same customer should be denied access to staff-only functions.
  • Session handling checks logout and idle expiry. After logout or expiration, protected pages should require sign-in.
  • Data protection checks that sensitive data travels over HTTPS and is excluded from error messages and logs. Verify that production configuration disables public directory listings.

Exam example. Use an approved test account, sign in, open order history, sign out and revisit the same page. Expect a sign-in request and no order details in the response.

Navigation testing

Navigation testing verifies that users reach the correct page, can return to a previous step and can recover if a page is unavailable. It covers internal links, external links, redirects and in-app search.

PathCheck
Internal linkCart → Checkout opens the correct page and preserves cart items.
External linkThe help link opens the intended support page.
RedirectAfter sign-in, the shopper returns to the intended checkout step, if the requirements specify that behavior.
Search and BackA result opens the matching product. Returning to search restores the filters if required.

Performance testing

Performance testing measures speed, stability and capacity at a specified workload. Decide a target before running a test, such as 100 concurrent users, a 95th-percentile response time of at most 2 seconds, and fewer than 1% failed requests.

MeasureInterpretation
Response time and round-trip timeResponse time measures how long a request takes from the defined measurement point. Network round-trip time measures travel to a remote endpoint and back.
Throughput and error rateRecord completed requests per second and the percentage of failed requests.
Utilization and database loadObserve CPU, memory, connection usage and query workload to identify bottlenecks.
ScalabilityRepeat at increasing workload or with additional resources and compare the results.

Load testing checks normal or expected peak conditions. Stress testing goes beyond that workload to find limits and observe failure and recovery. JMeter example. In a test environment, create a Thread Group for virtual users, an HTTP Request sampler for catalogue browsing and a results report. If p95 is 1.8 seconds but errors are 1.3%, the example above fails the error-rate target.

Past paper · Five challenges for 10 marks · Paper B, Q3(i)

Testing Agile software

In Agile, developers and testers work in short iterations. They clarify acceptance criteria during planning, design and run tests as the story is built, regress earlier features, then use review feedback to improve the next iteration. In test-driven development (TDD), a developer writes a failing test, writes enough code to pass it, then refactors while keeping the tests green.

Five challenges, with one response each

  1. Changing requirements. Existing cases can become stale. Refine acceptance criteria and update linked tests when a story changes.
  2. Regression risk. New features may break existing behavior. Run a prioritized regression suite frequently.
  3. Short iterations. A large test effort may exceed the sprint window. Start testing early and run fast checks on each change.
  4. Distributed teams. Different locations and time zones can delay answers. Keep acceptance criteria, test results and defects in shared records.
  5. Growing scope across sprints. More features and data make suites and environments harder to maintain. Keep reusable test data, remove redundant checks and assign maintenance ownership.

CI/CD pipeline stages and components

A commit triggers a build on a runner. Unit and integration checks run against the build. A passing artifact is stored and deployed to staging, where smoke or acceptance checks validate key flows. A failed required check blocks promotion. At the production step, delivery can wait for approval and deployment promotes automatically. Monitoring checks the release and supports rollback when necessary.

StageTypical output
SourceA versioned commit or pull request triggers a pipeline. A runner executes its jobs.
Build and testCompile or assemble the app and run automated checks. Publish test results.
Package and storeKeep a versioned build or container in an artifact registry so it can be promoted consistently.
StagingDeploy to a preproduction environment and run smoke or acceptance tests.
Release and monitorApply the production release policy, verify key flows and watch operational metrics for failures.

Common CI/CD tools

A CI/CD tool coordinates when jobs run, which runners execute them, where artifacts are stored and which checks or approvals govern promotion.

ToolExample use
GitHub ActionsRun a build and unit tests when a pull request changes in a GitHub repository.
JenkinsUse a Jenkins pipeline and build agents to run build, test and deployment jobs.
GitLab CI/CDDefine stages in a GitLab repository and run the jobs on GitLab runners.
Azure PipelinesBuild and test an application, then deploy it to a staging environment through a defined pipeline.

When selecting one, check repository integration, runner availability, artifact storage, environment access and test reporting.

CI vs CD

PracticeWhat happens
Continuous integration (CI)Integrate small code changes frequently and automatically build and test them to catch problems early.
Continuous delivery (CD)Automate validation and preparation so changes remain ready to release. A release decision or approval can control when production is updated.
Continuous deployment (CD)Automatically release eligible changes to production after required checks pass.

Checkout example. A tax-calculation change triggers an automatic build and tests during CI. In continuous delivery, the passing build is ready to release after a production decision. In continuous deployment, the passing build goes to production automatically under the defined rules.

Role of AI in automation

AI can draft test cases from requirements, suggest which regression tests to run first using change and failure history, and group similar failures for triage. Testers validate the proposed checks before adding them to the automated suite.

  • Test design. Suggest cases from user stories and test data for uncommon combinations.
  • Execution planning. Use changed components and past failures to suggest which approved regression tests to run first.
  • Result analysis. Group similar failures to reduce duplicate investigation. Testers confirm the cause before assigning a defect.
  • Maintenance. Suggest script or locator updates after intentional UI changes. Review changes to preserve what the original assertion checks.

Intelligent test case generation

Process. Provide the user story, rules and data constraints. Ask the tool to propose normal, invalid and boundary cases with steps and expected results. Check every expected result against the requirement, remove duplicates, and link approved tests to the relevant story.

Example. A shop offers free shipping for valid whole-rupee cart totals of ₹500 or more. AI proposes ₹499 → shipping charged, ₹500 → free and ₹501 → free. A tester confirms the ₹500 case against the rule and clarifies how discounts affect the threshold before adding discount-related cases.

Record enough information to reproduce each case. For the free-shipping rule, include the precondition (a test cart and a valid address), the input (the cart total), the step (calculate shipping), and the assertion (shipping charge matches the rule). Track the user story and record any clarification needed before using the generated case.

What if the AI says a ₹500 total should still incur a charge?

Check the requirement for the expected result. The phrase ₹500 or more includes exactly ₹500, so the approved assertion is free shipping.

5 marks · What is the difference between CI, delivery and deployment?

CI integrates and automatically validates frequent code changes. Continuous delivery keeps them release-ready and allows a production decision or approval. Continuous deployment releases them automatically when the required checks pass.

5 marks · How would you use AI to make boundary tests safely repeatable?

Give the AI the requirement and valid data range. Request cases directly below, at and above the threshold. Verify expected results independently against the requirement. Save the approved inputs and assertions so future runs use the same checks.
