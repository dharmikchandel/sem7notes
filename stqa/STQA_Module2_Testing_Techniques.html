Boundary value analysis

CriticalAsked: Oct 2022, Sep 2023, Oct 2025About 45 minSyllabus 2.2

Black-box testing treats the software as a box: you choose inputs, look at outputs, and ignore the code inside. Boundary value analysis is its most useful technique, for one reason: programs break at the edges of ranges. A developer writes < where <= was needed, and only the value exactly on the edge shows it.

Three versions, one idea

Take each input variable, pick values at its edges, hold the other variables at a nominal (middle) value, and test.

Boundary value checking (BVC)
For each variable use: min, min+ (just above), max− (just below), max. Add one test with every variable nominal. For n variables: 4n + 1 tests.
Robustness testing
BVC plus values just outside the range: min− and max+. These check how the program handles invalid input. For n variables: 6n + 1 tests.
Worst-case testing
Let more than one variable sit on a boundary at the same time: try every combination of {min, min+, nominal, max−, max}. For n variables: 5n tests.

How to choose the nominal value

Pick the middle of the range, rounded down: (min + max) / 2. For [1,50] that is 25. Any sensible middle value is accepted, but use the same one every time.

The method, in the order you write it

  1. Write the range of each variable and its nominal value.
  2. List the boundary values for each variable (min, min+, max−, max, and min−, max+ for robustness).
  3. Build the table: vary one variable at a time while the others stay nominal, then add the all-nominal row.
  4. Fill the expected output by working out what the program should print.
  5. State the count with the formula.

Equivalence class testing

CriticalAsked: Sep 2023, Sep 2024, Sep 2025About 35 minSyllabus 2.2

Boundary analysis picks the edges. Equivalence class testing picks one representative from each group of inputs that the program treats the same way. If one value in a group finds a bug, any other value in it would too, so testing them all is wasted effort.

The idea

  • Split the input domain into equivalence classes. Every member of a class causes the same kind of processing and output.
  • Run one test case per class. This keeps the test count small while still touching the whole domain.
  • Two goals: completeness (cover the whole domain without running every value) and non-redundancy (do not run two tests from the same class).

Two steps: identify the classes, then design the test cases.

Valid and invalid classes

Valid classes
Inputs the program is meant to accept, inside the specified range or type.
Invalid classes
Inputs the program must reject or handle as errors: out-of-range values, wrong types, empty input. Do not test only valid inputs. Invalid inputs produce error conditions and unexpected behaviour.
Two rules for the test cases

One test case can cover several valid classes at once. Test invalid classes one at a time, with every other input valid. If you put two invalid values in one test, the program may reject at the first one and the second is never tested.

Equivalence class testing

A black-box method. The input domain is divided into equivalence classes. Every member of a class causes the same kind of processing and output.

  • Only one test case from each class is executed.
  • If one value in a class finds a bug, the others would too.
  • Goals: completeness and non-redundancy.
  • Steps: 1. identify classes, 2. design test cases.
  • Valid classes: inputs the program should accept. Invalid classes: inputs that should be rejected.

  • Valid: 1 <= A <= 100, 20 <= B <= 40.
  • Invalid: A < 1, A > 100, B < 20, B > 40.
  • Tests: (50,30) accepted; (0,30), (101,30), (50,19), (50,41) rejected.

Valid equivalence classes consider valid inputs to the program, those inside the specified range or type, which it should accept.

Static testing: inspection, walkthrough, review

CriticalAsked: Sep 2024, Sep 2025About 30 minSyllabus 2.1

Static testing finds defects without running the software. People read and examine requirements, designs and code. It is also called non-computer-based or human testing, and it is how most verification activities (Module 1, Lesson 5) are carried out.

Why it exists

Dynamic testing has drawbacks: it finds bugs late in the SDLC, which makes them costly to fix; it is expensive and slow because test cases must be created, run and maintained; and tracing a failure back to its cause is hard. Static testing complements it and reveals errors that dynamic testing does not show.

Benefits

  • Defects found and fixed early raise quality.
  • Each new phase starts from a technically correct base.
  • Life-cycle cost is lower.
  • Dynamic testing becomes more effective and needs less time.
  • Authors get immediate feedback from peers.

Objectives

  • Find errors in any SDLC phase as early as possible.
  • Check that components conform to requirements.
  • Provide information for project monitoring.
  • Improve software quality and productivity.

The three techniques

Your slides name three: software inspections, walkthroughs and technical reviews. Inspection is the most formal, the walkthrough is looser, and the technical review involves management.

Inspection

An in-process, manual examination of an item to detect bugs. It can be applied to any product of development: requirements, design, code, project and quality plans, test cases, user manuals. It is done early, needs no executable code and no test cases, and can find bugs on rarely executed paths that tests would miss.

Team: author (owner or producer), inspector, moderator, recorder.

Process:

  1. Planning. Plan the inspection meeting.
  2. Overview. Define the purpose of the meeting.
  3. Individual preparation. Each member studies the item and notes potential errors.
  4. Inspection meeting. The item is inspected and the bugs are recorded.
  5. Rework. The author fixes the reported bugs.
  6. Follow-up. Check that the fixes were made; re-inspect if needed.
Measuring it

Error detection efficiency = (errors found by an inspection / total errors in the item before the inspection) × 100.

Benefits include bug reduction and prevention, higher productivity, real-time feedback to engineers, quality improvement, finding the most error-prone modules, learning through inspection, and process improvement.

Structured walkthrough

A less formal and less rigorous technique than inspection. The author presents the work product step by step to a small group, who ask questions and point out problems.

Team:

  • Coordinator: organises and runs the walkthrough.
  • Presenter / developer: explains the product, step by step.
  • Scribe / recorder: writes down issues and decisions.
  • Maintenance representative: checks that the product can be maintained.
  • Standards bearer: checks that standards are followed.
  • User representative / accreditation agent: checks that it meets the user's needs.

Process: organisation, then preparation, then the walkthrough itself, then rework and follow-up.

What the roles do

Your slide lists the roles only by name. The one-line descriptions above are the standard meanings, added so you can write a full answer.

Technical review

Evaluates the software against development standards, guidelines and specifications, and gives management evidence that development is following its stated objectives. It is like an inspection or walkthrough, except that the review team includes management and project management. It is considered a higher-level technique.

Regression testing

CriticalAsked: Sep 2025About 25 minSyllabus 2.3

Fix one thing, break another. When software changes, parts that worked before can stop working. Regression testing runs tests again after a change to prove that nothing else was damaged.

Why it is needed

  • When a new module is added during integration, new data-flow paths and new input and output appear. Modules that worked can be affected.
  • When a bug is fixed, the change itself may affect other parts of the software.
  • So whenever the software configuration changes, the software is tested again with the existing test cases.

Definition

Regression testing is the selective retesting of a system or component to verify that modifications have not caused unintended effects, and that the system still complies with its specified requirements. It is a maintenance task performed on a modified program to build confidence that the changes are correct and have not harmed the unchanged parts.

A system regresses if a modified component fails, or if a new component causes failures in unchanged components through side effects or feature interactions. The versions involved:

Baseline version
A version that has passed a test suite.
Delta version
A changed version that has not yet passed a regression test.
Delta build
An executable configuration containing the delta and baseline components.

Objectives

  1. Check that the bug has been addressed.
  2. Find other related bugs.
  3. Check the effect of the change on other parts of the program.

When it is performed

Every time the software changes: after a bug fix, after a new feature or enhancement, when a new module is integrated, and after a change of configuration or environment. Run it before the changed build is released.

Why it matters

  • It validates the parts of the software where changes occurred.
  • It validates parts that may be affected by the change, even if they seem unrelated.
  • It keeps the software working as it did before the change.
  • It raises quality by lowering the risk of serious bugs.

Types

Bug-fix regression
Done after a bug is reported and fixed. Repeats the test cases that exposed the problem in the first place.
Side-effect (stability) regression
Retests a substantial part of the product to show the change has no harmful effect on what was already working. It tests the overall integrity of the program, not whether the fix succeeded.

The problem, and how it is managed

Regression testing is expensive: large systems take a long time to retest, tests are slow to create and evaluate, and the cost can eat resources that could improve the software. Three techniques keep it affordable:

  • Regression test selection: pick only the tests relevant to the change (selective retest).
  • Test case prioritisation: run the most important tests first.
  • Test suite reduction: remove redundant tests.

Usability and accessibility testing

CriticalAsked: Oct 2022, Oct 2025About 30 minSyllabus 2.2

Not in your slides

The syllabus lists this topic and two papers asked it, but neither Chapter 1 nor Chapter 2 covers it. This lesson is taught from standard references (Nielsen's usability attributes, the WCAG guidelines). If your lecturer gave a specific definition in class, use that wording and add the points below.

Usability testing

Usability testing checks how easily and pleasantly real users can get their tasks done with the software. It asks "can people use this?", not "does it work?". It is done by watching representative users attempt realistic tasks.

What a usable system looks like (Nielsen's five attributes):

  • Learnability: a first-time user can do basic tasks quickly.
  • Efficiency: an experienced user can work fast.
  • Memorability: someone returning after a break does not have to relearn.
  • Errors: few mistakes, and easy recovery from the ones that happen.
  • Satisfaction: users find it pleasant to use.

How it is done:

  1. Define the goals and the tasks to test, for example "buy a book as a new user".
  2. Recruit users who match the real audience.
  3. Observe each user doing the tasks, often asking them to think aloud.
  4. Measure: task completion rate, time on task, number of errors, satisfaction rating from a short questionnaire.
  5. Analyse the problems, fix the design, and test again.

Example

An online bookstore. Task: "Find a novel and complete the purchase." Illustratively, suppose 6 of 10 test users cannot find the "Place order" button because it sits below the visible screen on a phone. Completion rate is 40 percent, which is a clear usability defect. Moving the button and retesting is the fix.

Accessibility testing

Accessibility testing checks that people with disabilities can use the software: users who are blind or have low vision, are deaf, have limited motor control, or have cognitive difficulties. It also helps everyone using a small screen, bright sunlight or a broken mouse.

The reference standard is WCAG (Web Content Accessibility Guidelines), built on four principles, often remembered as POUR:

Basis path testing and cyclomatic complexity

CriticalAsked: Sep 2025 (as an option)About 40 minSyllabus 2.2

This is a white-box technique: you use the code. Turn the program into a flow graph, count how many independent paths it has, and write one test case for each. If every independent path is run, every statement and every branch has been executed at least once.

Flow graph notation

  • Node: one or more procedural statements, drawn as a circle.
  • Edge (link): flow of control, drawn as an arrow. An edge must end at a node.
  • Decision node: a node with more than one arrow leaving it.
  • Junction node: a node with more than one arrow entering it.
  • Region: an area bounded by edges and nodes. The area outside the graph counts as a region too.

Cyclomatic complexity V(G)

V(G) is the number of independent paths through the graph, and so the number of test cases basis path testing needs. An independent path introduces at least one new set of statements or new condition, so it travels along at least one edge not used by the earlier paths. There are three formulas, and they must all give the same answer:

FormulaMeaning of the letters
V(G) = e − n + 2pe = edges, n = nodes, p = connected components (1 for a single program)
V(G) = d + pd = decision nodes. For one program this is d + 1
V(G) = number of regionsCount the bounded areas and the outside area

The method

  1. Number the statements and group them into nodes. Draw the flow graph.
  2. Compute V(G) with all three formulas. If the answer differs, recount.
  3. List V(G) independent paths.
  4. For each path choose input values and write the expected output. That is your test case.

Decision table testing

MajorNever asked yetAbout 25 minSyllabus 2.2

Boundary values and equivalence classes treat each input alone. When the output depends on a combination of conditions, a decision table lists every combination and what should happen for each.

Parts of a decision table

  • Condition stub: the list of conditions (the inputs).
  • Action stub: the list of possible actions (the outputs).
  • Rules: the columns. Each rule is one combination of condition entries (T, F, or a dash for "does not matter") and the actions that follow.

To get test cases: conditions become the inputs, actions become the expected output, and each rule is one test case. With k rules over n binary conditions you need at least k and at most 2n test cases.

Worked example from your slides

Salary program

If working hours are 48 or fewer, pay the normal salary. Hours above 48 on normal days are paid at 1.25 times the salary. On holidays or Sundays the hours are paid at 2.00 times. Design test cases using a decision table.

Rule 1Rule 2Rule 3
C1: hours ≤ 48TF–
C2: holiday or SundayFFT
A1: normal salaryX
A2: 1.25 × salaryX
A3: 2.00 × salaryX

Two binary conditions allow up to 22 = 4 rules. Rule 3 ignores C1 because the 2.00 rate applies on a holiday or Sunday whatever the hours, so three rules are enough.

Black-box versus white-box, and logic coverage

MajorNever asked yetAbout 20 minSyllabus 2.2

Dynamic testing means executing the code. It has two families, and your syllabus lists techniques from both.

Black-box (functional)White-box (structural, glass-box)
Looks atInputs and outputs. The inside is ignored.The design, structure and code.
Usually done byTestersDevelopers, on their own code
StageSecond stage of testingInitial stage, the module level
FindsWrong or missing functions, interface errors, performance and load problemsLogic errors, unexecuted paths, typing mistakes that black-box tests miss
Techniques hereBoundary values, equivalence classes, decision tablesLogic coverage, basis path, loop, data flow, mutation

The two are complementary. Some bugs show up only in white-box tests, for example a logical path you believed was rare but runs daily, or a typo that no functional test happens to hit.

Logic coverage criteria

These say how thoroughly a set of tests has exercised the code. Take this decision: if (A && B) x = 1;

CriterionRequirementTests for the example
Statement coverageEvery statement runs at least once. Necessary, but not sufficient.(A, B) = (T, T). One test.
Decision (branch) coverageEvery decision is true once and false once.(T, T) and (F, T). Two tests.
Condition coverageEvery condition inside a decision is true once and false once.(T, F) and (F, T). Two tests.
Multiple condition coverageEvery combination of condition outcomes.(T,T) (T,F) (F,T) (F,F). Four tests.
A trap in the table

The two condition-coverage tests (T, F) and (F, T) make the whole decision false both times, so condition coverage does not guarantee decision coverage. That is why multiple condition coverage exists.

Loop testing

MajorNever asked yetAbout 10 minSyllabus 2.2

Loop testing extends branch coverage. Loops are important because mistakes in how many times they run, such as the classic off-by-one, can go undetected.

Simple loop

Your slide gives these checks. Let the loop run at most n times:

  • Check whether the loop can be bypassed. If the bypass test runs and you still enter the loop, there is a bug.
  • Check whether the loop control variable can be negative.
  • One test that executes the statements inside the loop.
  • Tests for a typical number of passes.
  • Tests at the boundaries of the iteration count: minimum, min+1, min−1, max−1, max, max+1 passes.
Passes through a loop that runs at most n timesWhat it checks
0The loop is skipped correctly
1 and 2First iteration, and that a second one starts
m, where m < nA typical number of passes
n−1, n, n+1The boundary: last allowed passes, and one too many

Nested and concatenated loops

  • Nested loops: start with the innermost loop, holding the outer loops at their minimum. Test it as a simple loop. Then move outward one level, keeping the inner loops at typical values.
  • Concatenated loops (one after another): if they are independent, test each as a simple loop. If the second depends on the first, for example it uses the first loop's counter, treat them as nested.

Data flow testing

MajorNever asked yetAbout 15 minSyllabus 2.2

A white-box technique that finds improper use of data caused by coding errors, by studying how each variable is defined, used and killed.

States of a data object

  • d, defined: given a value (assigned or read in).
  • u, used: its value is read, in a calculation or a condition.
  • k, killed (undefined or released): its value is no longer valid, for example a freed pointer or a variable out of scope.

Anomalies: two states in a row

Look at pairs of consecutive actions on the same variable along a path.

PairMeaningVerdict
dudefine, then useNormal
uduse, then defineAllowed
ukuse, then killAllowed
kdkill, then defineAllowed
uuuse, then useAllowed
dkdefine, then kill with no usePotential bug
kukill, then useSerious bug
dddefine, then define again with no useHarmless bug, but not allowed
kkkill, then killHarmless bug, but not allowed
Remember

The pairs that are always trouble all repeat or waste something: dk, ku, dd, kk.

Tiny example

1  x = 10;        // d(x)
2  y = x + 5;     // u(x), d(y)
3  x = 20;        // d(x)
4  x = 30;        // d(x) again: dd anomaly, the 20 was never used
5  print(y);      // u(y)

Static versus dynamic

  • Static data flow testing: analyse the source code without running it. It is not enough, because it cannot tell which paths actually run.
  • Dynamic data flow testing: run the code. Test cases are designed so that every definition is traced to each of its uses, and every use is traced back to each of its definitions.

Mutation testing

MajorNever asked yetAbout 15 minSyllabus 2.2

Mutation testing does not test the program. It tests your tests. Put a small error into the code, run the tests, and see whether they notice. If they do not, the tests are weak.

  • A faulty copy of the program is a mutant. Each mutant contains one fault.
  • A mutant is killed when some test case makes it fail, that is, its output differs from the original program's. A dead mutant has done its job and leaves the process.
  • A mutant that survives every test is alive. It means the test data is not good enough, and you add a test that kills it.
  • Primary mutants come from one change in the code. Secondary mutants come from two or more changes.

Example from your slides

if (a > b)
    x = x + y;
else
    x = y;
printf("%d", x);

Primary mutants: M1 x = x − y. M2 x = x / y. M3 x = x + 1. M4 print y instead of x. Adding one more, M5, changes the condition to a >= b. Try three tests with x = 2, y = 4 (K means killed, A means alive):

Test (a, b)OriginalM1M2M3M4M5
t1: (5, 3)6KKKKA
t2: (3, 5)4AAAAA
t3: (3, 3)4AAAAK

t1 kills four mutants. t2 kills none, so it adds nothing for mutation purposes. M5 survives until t3, where a equals b, exposes it. Without a test with a = b, a real boundary bug of that kind would also survive.

Extra point

The mutation score = killed mutants / total mutants. It is a standard measure, not in your slides, but it makes a good closing line.

Secondary mutants from your slide

For if (a < b) c = a; the slide shows if (a <= b-1) c = a;, if (a+1 <= b) c = a; and if (a == b) c = a+1;. Each has more than one change, which makes it secondary.

One test per class. Valid classes can share a test. Invalid classes one at a time. Largest of three: I1 to I3 valid, I4 to I9 invalid, plus 7 output classes covered by 4 tests (11 total).
Decision table
Conditions are inputs, actions are outputs, each rule is a test. k rules on n binary conditions: at least k, at most 2n tests.

Coverage
Statement, decision (branch), condition, multiple condition.
Loops

Data flow
States d, u, k. Trouble pairs: dk, ku, dd, kk.
Mutation

Static
