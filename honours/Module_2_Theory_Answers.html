01

Infection vectors and first triage

supportUnit 2.1·10 min·Begin here
+
Why this matters: Start every analysis with a purpose, not random clicks.

From suspected file to investigation

An infection vector is the way malicious code first reaches a system: phishing attachment, malicious download, compromised site, exposed vulnerable service or removable media. A dropper installs a payload; a downloader fetches it.

1Identify the sampleName, source, file type, size, time and hash
2Ask what is suspiciousUnexpected origin, fake icon, unusual executable properties
3Perform basic static analysisAV results, hashes, strings, PE information and imports
4Execute only in an isolated labRecord process, file, registry and network effects
5Correlate and reportSeparate observed facts from interpretation

The goal is to learn the malware's purpose, installation, persistence and observable indicators rather than manually exploring every function.

✍ Exam writing plan

5 marks: explain initial infection vectors (3 examples) and the first two malware-discovery steps. 10 marks: include a 5-step analysis methodology and reasons to use isolation.

Common mistake: Do not run an unknown sample on your main laptop just to see what happens.
Test yourself before revealing

What is the first artifact you should record before deeper inspection?

Show answer

Basic metadata and a cryptographic file hash, so the sample can be identified consistently.

📚 Sources: Ch04-Malware, slide 30; PMA, Chapters 0–3.
02

Basic static analysis: the exam-ready workflow

ASKED IN PYQcoreUnit 2.1·18 min·Very important
+
Why this matters: Know what each technique answers and what it cannot prove.

Static analysis inspects a file without executing it. It is usually the safest first technical step.

StepWhat to inspectInterpretation
1. Antivirus / VTMulti-engine alertsEarly clue, not verdict
2. HashMD5 / SHA-256Fingerprint for matching/sharing
3. StringsURLs, domains, paths, commandsHints at configuration and behavior
4. PE structureHeader, sections, entry point, importsFile layout, APIs, likely packing
5. ImportsWindows API functions and DLLsPossible network, file or process actions
6. DisassemblyInstructions, branches and callsDetailed logic when surface clues fail

Interpret suspicious Windows imports

CreateFile / WriteFile can suggest file activity; RegSetValueEx registry modification; InternetOpen/InternetConnect network use; CreateProcess process creation. One API import never proves malicious intent.

Possible packing indicators: high entropy, few strings, tiny import set, unusual PE sections. When a file is packed, static analysis may reveal only an unpacking stub.

Static strengths: safer, fast, repeatable, no run-time side effects. Limitations: packing/obfuscation; string presence does not prove code executes; precise behaviors may be hidden.
✍ Exam writing plan

10 marks: define static analysis (1), six techniques with expected findings (6), strengths (1), limitations (2). Use the table above. 5 marks: hashing, strings, imports, PE and scanning.

Common mistake: Suspicious imports or strings are hypotheses to test, not conclusive detection.
Test yourself before revealing

What do hashes and strings reveal, respectively?

Show answer

Hash identifies the exact file bytes for lookup/coordination; strings reveal possible URLs, filenames and other clues to behavior.

📚 Sources: PMA, Chapter 1: Basic Static Techniques; Ch04-Malware, slides 24–30.

Basic dynamic & behavioral analysis

ASKED IN PYQcoreUnit 2.1·17 min·Very important
+
Why this matters: The easiest long-answer comparison is static versus dynamic plus tools and observations.

Dynamic analysis studies a program while it runs or after it has executed, in a controlled environment. It answers what actually happened on the tested run.

What to monitorTool exampleEvidence
Processes & DLLsProcess ExplorerNew child processes, unusual loaded modules
Files & registryProcess Monitor (Procmon)Created executable, modified Run key
Before/after registryRegshotNew or changed keys
Network trafficWiresharkDNS lookups, outbound connections, HTTP requests

Static vs dynamic: answer in 20 seconds

Static

No execution, fast/safer; exposes structure and possible intent; hindered by packing.

Dynamic

Runs sample in isolation, exposes actual observed behavior; higher risk; may miss dormant/hidden execution paths.

Example: a suspicious process creates an autorun registry entry and repeatedly queries an unknown domain. The first suggests persistence; the second suggests potential beaconing. Correlate before concluding.

✍ Exam writing plan

10 marks: definition → tools and monitored artifacts → 5-step workflow → static/dynamic comparison → limitations. 5 marks: static/dynamic comparison table with four differences.

Common mistake: A single run does not cover every execution path; malware may delay execution or detect a sandbox.
Test yourself before revealing

Which tool is best associated with viewing process trees, and which with file/registry operation logs?

Show answer

Process Explorer for process trees and modules; Procmon for file, registry and process operation events.

04

Windows PE files: what is inside an EXE?

supportUnit 2.1·11 min·Quick technical marks
+
Why this matters: You do not need the entire PE specification. Learn sections, imports and the entry point.

Most Windows executables and DLLs use PE = Portable Executable format. A PE file has headers and sections; headers help Windows load the file.

Simplified PE file map
PE headersFile type, architecture, entry point, section table
.textExecutable instructions
.rdataRead-only constants / import-related data (typical)
.dataInitialized writable globals
.rsrcIcons, dialogs, embedded resources

Imports list functions the program uses from libraries (for example, Windows APIs). Exports list functions a DLL provides to other programs. Entry point is where execution begins after loading, not necessarily the original programmer's main().

Possible signs of packing: unusual section names, inconsistent section sizes/entropy, unexpectedly sparse imports. Tools in the source include PEview, Dependency Walker and Resource Hacker.

✍ Exam writing plan

5 marks: define PE (1), headers (1), any three sections (3). 10 marks: add import/export table, entry point, static-analysis uses and packing clues.

Common mistake: The location and naming of sections are typical conventions; exact sections vary by executable.
Test yourself before revealing

What is the difference between an import and an export in a PE file?

Show answer

An import names a library function the file uses; an export is a function the file makes available to other modules.

📚 Sources: PMA, Chapter 1: Portable Executable Format, linked libraries, headers and sections.
05

x86 assembly: registers and instructions

coreUnit 2.2·19 min·Must understand
+
Why this matters: You can gain many marks by reading a dozen opcodes correctly.

x86 assembly is a human-readable representation of machine instructions. For the syllabus, focus on 32-bit Intel syntax and the idea that instructions change registers, memory or flags.

RegisterExam meaning
EAXGeneral purpose; commonly return value
EBX, ECX, EDXGeneral purpose; ECX often used as a counter
ESPStack pointer (top of stack)
EBPFrame/base pointer (common unoptimized convention)
EIPInstruction pointer (next instruction)
EFLAGSStores status flags used by conditional jumps

Read the instructions

mov eax, 5     ; EAX = 5
add eax, 3     ; EAX = 8
sub eax, 1     ; EAX = 7
xor ebx, ebx   ; EBX = 0
push eax       ; place EAX on stack
pop ecx        ; read stack top into ECX

Intel notation: destination first, source second: mov eax, ebx copies EBX into EAX. Square brackets mean memory dereference: mov eax,[ebp-4] loads a value from a stack-frame location. lea eax,[ebp-4] computes its address, not the contents at that address.

Memory aid: MOV copy; ADD/SUB arithmetic; CMP/TEST update flags; Jxx branch; CALL/RET function flow; PUSH/POP stack.
✍ Exam writing plan

10 marks: define x86, describe six registers, explain six common instructions with a small arithmetic example. Short question: difference between mov and lea.

Common mistake: mov copies a value; it does not “move” from source by deleting the source. Also, [eax] means memory at address EAX.
Test yourself before revealing

After mov eax,5; add eax,3; sub eax,1, what is EAX?

Show answer

EAX = 7.

📚 Sources: PMA, Chapter 4: x86 Architecture; intro-binary-reversing, page 5.
06

Trace if-statements, loops and function calls

coreUnit 2.2·16 min·Practice example
+
Why this matters: Examiners can give a short assembly snippet and ask for its logic.

Walk an if statement

mov eax, 7
cmp eax, 5       ; compares 7 and 5
jg  greater      ; jump if signed 7 > 5
mov ebx, 0      ; skipped
jmp done
greater:
mov ebx, 1      ; executed
done:

Result: EBX = 1. cmp a,b sets flags as though computing a - b; the jump tests these flags. Common branch cues: je/jz equal/zero; jne/jnz not equal; jg greater (signed); jl less (signed); jmp unconditional.

Recognise a loop

mov ecx, 3
loop_start:
  sub ecx, 1
  cmp ecx, 0
  jne loop_start

Trace: ECX 3 → 2 → 1 → 0; loop body runs 3 times. A backward conditional jump often indicates a loop. Forward conditional jump often indicates a branch, but not universally.

Function control flow

call target saves a return address and jumps to a function; ret returns via the saved address. Stack-frame conventions often use push ebp; mov ebp,esp at entry, and mov esp,ebp; pop ebp; ret at exit, though compiled optimized code may differ.

3-step tracing method: write register values → execute instructions in order → evaluate comparison flags and take only the selected branch.
✍ Exam writing plan

5 marks: define CMP, JMP, conditional branch and CALL/RET, then trace a 4-line example. 10 marks: draw a flowchart, trace registers and compare if vs loop patterns.

Common mistake: Do not assume cmp stores its difference in the operands; it updates flags.
Test yourself before revealing

In the loop shown, how many times does sub ecx,1 execute?

Show answer

Three times. The final comparison sees ECX equal zero, so JNE is not taken.

📚 Sources: PMA, Chapters 4 and 6; Reverse Engineering, pages 9–10.
07

Sandboxing and safe VM analysis

supportUnit 2.2·11 min·Safety + method
+
Why this matters: Learn a safe, reproducible workflow and why automated sandboxes can miss behavior.

A sandbox is a controlled environment for observing untrusted code without letting it affect ordinary systems. A virtual machine (VM) runs a guest OS under a hypervisor. Isolation is a risk reduction, not a guarantee.

1PrepareDedicated analysis VM, patched host, isolated networking and no shared secrets
2SnapshotSave a clean baseline to revert to
3MonitorRecord baseline processes, registry and network before testing
4ObserveRun only authorized safe samples in a purpose-built lab
5Collect & revertSave evidence and restore the clean snapshot

Network caution: use no network or carefully simulated/controlled services as appropriate, not a bridge to production systems. Avoid unnecessary shared folders and clipboard access. Limitations: anti-VM detection, delayed behavior, missing C&C responses and unexplored command-line options.

Automated sandboxes produce useful file, registry, process and network activity reports; manual analysis can investigate paths the automated run did not trigger.

✍ Exam writing plan

10 marks: define sandbox/VM, explain five-step method, list three benefits and three limitations. 5 marks: explain snapshots and isolation.

Common mistake: A snapshot does not make arbitrary malware safe if the VM can reach your host or live network.
Test yourself before revealing

Why revert to a clean VM snapshot after analysis?

Show answer

It restores the controlled baseline and removes modifications from the observed run, improving repeatability.

📚 Sources: PMA, Chapters 2 and 3; PMA warning and sandbox limitations.
08

Runtime memory: stack, heap and code

coreUnit 2.3·16 min·Draw this
+
Why this matters: Memory layout and registers are the bridge into all overflow questions.

Each process uses virtual memory. The OS and runtime organize it into regions that serve different roles. The address arrangement below is conceptual; real layouts vary with architecture, OS and ASLR.

Simplified process address space · conceptual
.text / codeInstructions, generally read + execute
.rodataRead-only constants
.data / .bssInitialized / uninitialized globals
Heap ↑Dynamic allocations; lifetime controlled by allocator
Free / mapped areaLibraries and mapped memory also occupy virtual space
Stack ↓Function frames, locals, return addresses

Stack

Organized by nested function calls; allocation generally automatic on function return. ESP marks top; EBP commonly anchors a frame.

Heap

Dynamic memory requested during execution. Wrong lifetimes may cause use-after-free or double free.

A stack frame often contains function arguments, return address, saved frame pointer and local variables. call places a return address on the stack; ret uses it to resume the caller.

✍ Exam writing plan

10 marks: draw regions (code/data/heap/stack), explain each, compare stack and heap, then show a simplified stack frame with saved EIP/EBP. 5 marks: stack vs heap in a table.

Common mistake: Heap and stack growth directions are common conventional diagrams, not a promise about every platform.
Test yourself before revealing

Which memory area normally stores call return addresses, and which is used for dynamic allocation?

Show answer

The stack typically holds return addresses; the heap provides dynamic allocations.

📚 Sources: 03.pdf, slides 3–6 and 19; PMA, Chapter 4.
09

Stack buffer overflow: from bug to control-flow change

ASKED IN PYQcoreUnit 2.3·18 min·Must know
+
Why this matters: A clear stack diagram and cause–effect chain can carry a full 10-mark answer.

A buffer overflow happens when input writes beyond an allocated buffer. In a stack buffer overflow, a long copy can overwrite nearby data, including a saved return address if the layout permits.

void bad(const char *s) {
    char buf[64];
    strcpy(buf, s);   // no check that s fits
}
Before overflow · illustrative
buf[64]Local bytes
Saved EBPCaller frame pointer
Saved EIPReturn address
After oversized copy · illustrative
AAAA...Buffer overwritten
AAAASaved frame data corrupted
AAAASaved return address corrupted

Cause → effect: unsafe copy → writes past buffer → possible saved return-address corruption → program crash or unintended control flow when ret executes. The lecture's AAAA bytes correspond to 0x41414141, illustrating a corrupted return address.

In a classical unprotected case, an attacker might exploit control-flow corruption. Modern mitigations complicate that, so an overflow does not automatically mean code execution.

Exam connection: stack canaries detect overwrites; ASLR makes target addresses unpredictable; DEP/NX makes data pages non-executable; memory-safe coding avoids the overflow.
✍ Exam writing plan

10 marks: definition → unsafe strcpy example → before/after frame diagram → control-flow impact → four defenses. 5 marks: describe cause, EIP corruption and two protections.

Common mistake: Do not write that every overflow overwrites EIP or always succeeds as an exploit. Layout and protections matter.
Test yourself before revealing

Why does overwriting the saved return address affect control flow?

Show answer

The RET instruction restores the instruction pointer from that saved address. If the value is corrupted, execution may jump incorrectly or crash.

📚 Sources: 03.pdf, slides 4–18; PMA, Chapter 4 (stack and CALL/RET).

Heap, integer and format-string vulnerabilities

ASKED IN PYQskimUnit 2.3·12 min·Short notes
+
Why this matters: Read for definitions, differences and quick examples. Avoid studying complex exploit chains.
VulnerabilityHow it happensPossible result
Heap overflowWrite beyond a heap allocationCorrupted neighboring objects or pointers
Use-after-freeAccess memory after it is freedStale reference; unintended behavior
Double freeFree the same allocation twiceAllocator state corruption
Integer overflowArithmetic exceeds numeric rangeWrong size calculation leading to undersized buffer
Format-string bugUser-controlled text treated as format templateUnexpected memory reads/writes or crash

One safe coding example

// Risk: attacker-controlled text is a format string
printf(user_input);

// Better: text is always data
printf("%s", user_input);

Integer overflow example: computing count * element_size with insufficient numeric range can wrap, producing an allocation too small for the intended data.

Defenses: bounds checks, checked arithmetic, safe format usage, well-defined ownership, fuzzing, and memory-safe languages where possible.

✍ Exam writing plan

5 marks: define any two vulnerability types, give a consequence and mitigation for each. 10 marks: compare stack vs heap overflow, and explain integer and format-string bugs.

Common mistake: An integer overflow is arithmetic wraparound; a buffer overflow is an out-of-bounds memory access. The first can contribute to the second.
Test yourself before revealing

Why is printf("%s", user_input) safer than printf(user_input)?

Show answer

The fixed format string prevents the input from being interpreted as formatting directives.

Protection mechanisms: canary, ASLR, DEP, fuzzing

coreUnit 2.3·19 min·Top exam essay
+
Why this matters: Memorise a one-line purpose and limitation for each defense.
DefenseWhat it doesRemember
Stack canaryPlaces a check value between local stack data and critical control data; verifies before returnDetects certain overwrites
ASLRRandomizes memory locations of stack, heap, libraries and code regionsHarder to predict addresses
DEP / NX / W^XPrevents pages from being both writable and executable in typical configurationsData should not run as code
Shadow stackKeeps a protected duplicate of return addresses for comparisonReturn integrity
FuzzingRuns many generated/mutated test inputs to find bugsFind defects before release
Memory-safe languagesUse rules/checks that prevent many classes of unsafe memory accessPrevent errors by design

Protection in context

Unsafe copy→Canary may detect→ASLR complicates targeting→DEP blocks injected data code

The lecture also introduces return-to-libc and ROP (return-oriented programming): conceptual ways attacks may reuse already-executable code rather than run code on non-executable data pages. You only need the defensive implication here: no single protection is sufficient.

Pre-deployment defenses: testing/fuzzing and safer languages. Runtime defenses: canary, ASLR, DEP and shadow stack. Post-compromise containment: sandboxing and privilege limits.

✍ Exam writing plan

10 marks: define memory safety, explain canary (with frame sketch), ASLR, DEP/NX, shadow stacks, fuzzing, safe languages; add limitations and defense-in-depth. 5 marks: explain any three protections and give one line on each.

Common mistake: A canary mainly detects certain stack corruptions; ASLR does not fix the bug; DEP does not stop all code-reuse attacks.
Test yourself before revealing

Which defense randomizes addresses, and which makes ordinary stack data non-executable?

Show answer

ASLR randomizes locations; DEP/NX/W^X restrict execution from writable data pages.

📚 Sources: 03.pdf, slides 23–47 (canaries, ASLR, W^X, ROP, fuzzing, safe languages).

PYQ Q2(b) · 5 marks — What is malware analysis? Differentiate static and dynamic analysis

Definition (1 mark)

Malware analysis is the systematic examination of a suspicious file or program to understand its behavior, functions, effects and indicators of compromise, so it can be detected and contained.

Comparison (4 marks)

BasisStatic analysisDynamic analysis
ExecutionExamines the sample without running it.Observes the sample while/after it runs in an isolated environment.
InformationHashes, strings, executable headers, imported functions, assembly.File changes, registry edits, processes, network traffic and runtime behavior.
ToolsStrings, PEview, Ghidra, VirusTotal/hash lookup.Procmon, Process Explorer, Regshot, Wireshark, sandbox.

Example: Seeing an embedded URL in a binary is static evidence. Recording an actual connection to that URL in a safely isolated run is dynamic evidence. Both approaches complement one another.

PYQ Q2(b) OR · 5 marks — Different tools used for static malware analysis, with examples

Static analysis investigates a suspicious program without executing it. Common tools are:

  1. Antivirus / VirusTotal: compares a sample or known file hash against malware detections. Example: seeing whether antivirus engines recognize a file. Don't submit confidential samples to public services.
  2. Hashing utilities: generate MD5 or SHA-family fingerprints to identify or compare exact file contents. Example: checking whether two samples have the same hash.
  3. Strings utility: extracts readable ASCII/Unicode text. Example: spotting a domain, file path or command embedded in a binary.
  4. PE inspection tools (PEview / PEiD): inspect Windows PE headers, sections, imports, and signs of packing. Example: suspicious imports hinting at network communication.
  5. Disassembler / decompiler (Ghidra): converts machine code to assembly/pseudocode. Example: tracing conditional branches and potential persistence routines.

Conclusion: No single static tool proves a file is malicious; analysts combine several clues and verify conclusions where possible.

Source: Practical Malware Analysis, Chapter 1; GHIDRA.pdf, pages 9–10. SHA-family hashing here is a general-purpose example in addition to the text's MD5 discussion.

PYQ Q3 · 10 marks — Explain stack overflow, heap overflow and integer overflow with examples

Introduction (1 mark)

A memory-safety vulnerability occurs when a program performs unsafe memory access or calculations. Overflow-related errors can corrupt data, crash a program and, under some conditions, alter its control flow.

1. Stack overflow (3 marks)

Definition: A stack-based buffer overflow occurs when a program copies more data into a local stack buffer than it can hold, potentially overwriting nearby local data, the saved frame pointer, or the saved return address.

// Conceptual vulnerable C example
void bad(const char *input) {
    char buffer[16];
    strcpy(buffer, input); // no length check
}

Example: If input exceeds the available buffer capacity, data can spill beyond buffer. The lecture illustrates how a stack overflow may eventually overwrite a saved return address and disturb execution.

STACK FRAME (conceptual)
[ local buffer      ]  ← extra input begins here
[ saved frame ptr   ]  ← may be corrupted
[ return address    ]  ← may be corrupted

Protection: validate lengths, use bounded copying, compiler stack canaries and exploit mitigations such as ASLR/DEP. These mitigations reduce impact, but don't fix the unsafe copy.

2. Heap overflow (3 marks)

Definition: A heap-based buffer overflow occurs when a program writes beyond a buffer allocated dynamically on the heap, corrupting adjacent heap objects or allocator metadata.

// Conceptual vulnerable C example
char *buffer = malloc(16);
strcpy(buffer, input);  // input may exceed allocation
free(buffer);

Example: A long string written into a small dynamically allocated buffer can overwrite adjacent heap data. The lecture shows a neighboring function pointer being overwritten, which could redirect execution if that pointer is later used.

HEAP (conceptual)
[ allocated buffer ][ adjacent object ]
          └─ extra writes can cross this boundary

Protection: strict allocation-size checks, bounds-checked operations and memory-safe abstractions; allocator hardening can help limit consequences.

3. Integer overflow (3 marks)

Definition: An integer overflow happens when an arithmetic result is outside the range representable by a chosen integer type. Unsigned integers wrap modulo their range; in C, signed overflow is undefined behavior.

#include <stdint.h>
uint8_t x = 255;
x = x + 1;    // x becomes 0 (unsigned 8-bit wraparound)

Example: If a program computes an allocation size using unchecked arithmetic and the result wraps, it may allocate too little memory and later write beyond it. Thus, integer overflow can lead to a memory buffer overflow, but it is not itself the same thing as a buffer overflow.

Protection: check ranges before arithmetic, use checked arithmetic functions, select suitable integer types and validate allocation sizes.

VulnerabilityWhere the error occursOne-line memory hook
Stack overflowLocal buffer on stackInput exceeds a local buffer
Heap overflowDynamically allocated heap bufferWrite exceeds an allocated block
Integer overflowArithmetic / type-range handlingNumber exceeds representable range
How to score 10: 1-mark introduction + (definition, 2-line example, consequence/defense) × three vulnerabilities. Draw two tiny memory diagrams for stack and heap. Don't confuse integer overflow with a buffer overflow.

Static and dynamic malware analysis: workflow and comparison · 10-mark model answer

Definition: Malware analysis studies suspicious code to identify what it does, how it behaves and which traces can help detect and contain it.

Basic static analysis: inspect the file without executing it. Steps: record a hash, inspect antivirus findings, extract readable strings, check executable headers and PE sections, inspect imported functions and examine disassembly if required.

Basic dynamic analysis: execute a sample only in a purpose-built isolated lab; monitor new processes, file writes, registry changes, services, DNS requests and network connections. Compare the system against a clean baseline.

BasisStaticDynamic
Runs sample?NoYes, in isolation
Main evidenceStrings, hashes, imports, codeActual observed side effects
ToolsStrings, PEview, GhidraProcmon, Regshot, Wireshark
StrengthSafer initial triageShows actual executed behaviour
LimitationPacking/obfuscationUnexecuted branches and evasive malware

Conclusion: use static triage first, then controlled dynamic analysis; evidence from both gives a more reliable picture.

Sources: Practical Malware Analysis Chs. 1–3; Ch04-Malware.pdf p. 30.

x86 registers and assembly for malware analysis · 10-mark model answer

Introduction: x86 assembly represents CPU instructions in a human-readable form. Analysts read assembly when source code is unavailable.

  1. EAX: general-purpose register, frequently used for return values and arithmetic.
  2. EBX, ECX, EDX: general-purpose registers; ECX is frequently used for counters, although usage depends on compiler and convention.
  3. EIP: instruction pointer indicating the next x86 instruction to execute.
  4. ESP: points to the top of the stack; EBP commonly references a stack frame in traditional frame-pointer-based code.
  5. EFLAGS: stores condition flags used by conditional branches.
  6. MOV: copy data; ADD/SUB: arithmetic; CMP: compare by setting flags; JE/JNE/JG/JL: conditional jumps; JMP: unconditional jump.
  7. PUSH/POP: modify stack contents; CALL: call function and save a return address; RET: return using saved address.
mov eax, 4
add eax, 3
cmp eax, 7
je equal
mov ebx, 0
jmp done
equal:
mov ebx, 1
done:

Tracing: EAX becomes 7; CMP sets the equal condition; JE reaches equal, so EBX becomes 1.

Conclusion: understanding registers, stack behaviour and jumps helps translate disassembly into program logic.

Sources: PMA Ch. 4; Reverse Engineering.pdf, pp. 9–10.

Recognizing if statements, loops and calls in disassembly · 10-mark model answer

Introduction: compilers translate conditions and loops into comparisons and branches. A disassembler helps reconstruct the control-flow graph.

  1. If statement: CMP or TEST sets flags; a conditional jump chooses one branch.
  2. If–else: conditional branch selects an alternative block, with a later unconditional JMP often skipping the other branch.
  3. Loop: an update and a conditional branch repeat a block. Backward branches often indicate loops, but not always.
  4. Function call: CALL transfers to a function and stores a return address; RET brings control back.
  5. Tools: graph view in Ghidra or a disassembler displays branches and cross-references; a debugger can validate one path.
mov ecx, 0
again:
add ecx, 1
cmp ecx, 3
jl again

Trace: ECX takes values 1, 2 and 3. The JL branch repeats while ECX is less than 3, then execution falls through. This corresponds to a loop running three times.

Conclusion: identify flags, branch targets and repeated blocks rather than memorizing specific compiler output.

Sources: PMA Ch. 6; Reverse Engineering.pdf pp. 9–10.

Memory organization and stack-buffer overflow with diagram · 10-mark model answer

Introduction: a process uses memory regions for instructions, global/static data, dynamic allocations and function calls.

Conceptual process memory
+------------------+
| Stack: call frames|
+------------------+
| Heap: allocations|
+------------------+
| Data / BSS       |
+------------------+
| Code / text      |
+------------------+
  1. Code section: contains machine instructions; data contains initialized globals; BSS uninitialized globals.
  2. Heap: dynamically allocated storage whose lifetime is managed separately from calls.
  3. Stack: stores stack frames, often including local variables, saved frame data and a return address.
  4. Stack-buffer overflow: occurs when a write exceeds a local buffer boundary and can overwrite adjacent stack data.
void bad(const char *s) {
 char buf[16];
 strcpy(buf, s); // unsafe without a length check
}

Example: copying input longer than the buffer's capacity can corrupt nearby stack contents. In older illustrative x86 layouts, a large overflow may reach the saved return address and change control flow; it can also simply crash the program.

Defenses: bounds checking, safer API use, stack canaries, ASLR and non-executable memory.

Conclusion: overflow is fundamentally an out-of-bounds memory write; exploitation depends on layout and defenses.

Sources: 03.pdf pp. 4–10 and 23; PMA Ch. 4.

Heap overflow, integer overflow and format-string bugs · 10-mark model answer

Introduction: these vulnerabilities result from unsafe memory access, arithmetic assumptions or incorrect use of formatted-output functions.

  1. Heap overflow: writing beyond a dynamically allocated heap object can corrupt a neighbouring object, pointer or allocator metadata. Example: a program allocates 16 bytes and copies a longer string without checking its length. Possible outcomes include data corruption and crashes.
  2. Integer overflow: a calculation produces a value outside the range of its integer type. Unsigned arithmetic wraps modulo the type's range; signed overflow in C has undefined behaviour. Example: an 8-bit unsigned value 255 + 1 becomes 0. If software calculates allocation sizes without checking range, a too-small buffer may later be written out of bounds.
  3. Format-string vulnerability: untrusted input is used directly as a format argument. Example: printf(user_input) instead of printf("%s", user_input). Formatting directives in input may unexpectedly disclose information or otherwise affect program behaviour.

Comparison: heap overflow is a location-based out-of-bounds write; integer overflow is an arithmetic range error and can contribute to memory corruption; format-string bugs stem from interpreting user data as a formatting template.

Defenses: validated sizes, checked arithmetic, bounded writes, correct format strings, sanitizers and memory-safe languages.

Sources: 03.pdf p. 19 for heap examples; syllabus Unit 2.3 for integer and format-string topics. Detailed integer-overflow explanation supplements the supplied slides.

Protections: canaries, ASLR, DEP/NX, shadow stack and fuzzing · 10-mark model answer

Introduction: security defenses aim to prevent memory errors, detect corruption and make exploitation more difficult.

  1. Stack canaries: the compiler inserts a guard value between local data and sensitive saved stack state; checking it before return detects many stack overwrites.
  2. ASLR: Address Space Layout Randomization changes addresses of memory regions, making useful target addresses harder to predict.
  3. DEP/NX (W^X): non-executable data memory reduces the ability to run injected instructions directly from stack or heap regions.
  4. Shadow stack: maintains a protected copy of return addresses and checks them against regular stack entries.
  5. Bounds checks: validate indices, buffer sizes and input lengths to prevent invalid writes in the first place.
  6. Fuzzing: repeatedly tests software with varied inputs to expose crashes and unexpected behaviour before deployment.
  7. Memory-safe languages: reduce entire classes of unsafe memory operations through checked or managed memory access.

Limitations: no single mitigation eliminates every flaw; some protections detect exploitation attempts rather than preventing the underlying bug.

Conclusion: secure coding plus multiple defenses provides stronger protection than relying only on runtime mitigations.

Source: 03.pdf pp. 23, 31, 33 and following defense slides.

Sandboxing malware in a virtual environment · 10-mark model answer

Definition: a sandbox or virtual machine allows suspicious software to be observed within a controlled environment separated from ordinary production systems.

  1. Prepare lab: use a dedicated VM with appropriate monitoring utilities and a known-clean snapshot.
  2. Isolation: avoid connections to the production network; restrict host integration and unnecessary shared folders or devices.
  3. Baseline: record the initial process, file, registry and network state.
  4. Static triage: first inspect hashes, imports and strings to determine likely behaviour.
  5. Controlled run: execute only if the lab is suitable and authorized; use Procmon, Process Explorer, Regshot and Wireshark to record changes.
  6. Collect findings: note created files, registry persistence, new processes, DNS activity and possible command-and-control indicators.
  7. Restore: preserve results safely and revert the VM to a clean snapshot.

Limitations: samples may detect VMs, delay activity, require unavailable network services or execute only under special conditions. A VM is not a guarantee of perfect containment.

Conclusion: sandboxes provide strong behavioural evidence but should be combined with static and code-level inspection.

Source: PMA Chs. 2–3.
